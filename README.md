# CompareQuery

The script runs a SQL query on MS SQL Server, saves every result table to a file and writes a report. The second mode compares two such reports: for example, the query result before and after a change to the database, a procedure or the query itself. It also measures performance — time, CPU, reads and a per-statement profile of the query or of another session — which makes it a tool for optimization.

# CompareQuery

Скрипт выполняет SQL-запрос на MS SQL Server, сохраняет все результирующие таблицы в файлы и пишет отчет. Заодно он замеряет производительность — время, CPU, чтения и профиль по операторам запроса или чужой сессии, — поэтому годится и для оптимизации. Второй режим сравнивает два таких отчета: например, результат запроса до и после изменения базы, процедуры или самого запроса.

## Требования

Программа лежит в папке `src` (`src\CompareQuery.py`, `src\cq_mssql.py`, `src\cq_pg.py`, `src\CompareQueryGUI.py`, `src\gui`), документация и лаунчер `CompareQueryGUI.exe` — в корне. В примерах ниже `CompareQuery.py` — это `src\CompareQuery.py`. Файл настроек `CompareQuery.json` — рядом со скриптом, то есть в `src`.

- Python 3.10 или новее.
- Модуль pyodbc: `pip install pyodbc`; для PostgreSQL — psycopg: `pip install "psycopg[binary]"` (см. «PostgreSQL»).
- ODBC-драйвер для SQL Server, лучше «ODBC Driver 17/18 for SQL Server».
- Право `VIEW SERVER STATE` для логина, чтобы были счетчики времени, CPU и чтений (см. «Контрольное подключение»). Без него запрос выполняется и сравнивается, но счетчиков в отчете не будет.

Для режима 2 (сравнение) pyodbc и сервер не нужны.

## Быстрый старт

1. Напишите тестовый скрипт `query.sql`: `SELECT` по таблицам, результат которых должен остаться прежним.
2. Запустите `python CompareQuery.py query.sql --repeat 2` и перенесите элемент из `# Предложение для настроек` в `ignored_columns`. Чтобы маска подходила и к копиям скрипта, расширьте ее: `query*`. Результаты этого запуска удалите.
3. Запустите скрипт один раз или с `--repeat N`: это образец.
4. Сделайте копию скрипта (`query_v2.sql`), измените ее или базу.
5. Запустите копию, лучше так же, как образец. С `--profile` будет видно, на что уходит время.
6. Сравните: `python CompareQuery.py <образец>.txt <новый>.txt`.
7. Посмотрите `..._compare_..._short.txt`, при необходимости полный отчет, данные и реестр операторов. Ненужный запуск удалите: отчет `<имя>_<время>.txt`, в подпапке `<имя>` файлы `<имя>_<время>_N.csv` и папку `<имя>_<время>_profile`, файлы сравнения `..._compare_<время>.txt` и `_short.txt`. Удачный оставьте образцом, главным или промежуточным.
8. Следующая итерация — с шага 4.

## Первый запуск и настройки

Настройки лежат в файле `CompareQuery.json` рядом со скриптом, а не в текущей папке. Если файла нет, скрипт создает его с примером и сообщает об этом. В режиме 1 после этого он завершается: сначала заполните настройки.

```json
{
  "connection_string": "Driver={ODBC Driver 18 for SQL Server};Server=localhost;Database=master;TrustServerCertificate=yes",
  "login": "sa",
  "password": "",
  "ignored_columns": [
    { "mask": "Report*", "tables": { "*": ["CreatedAt"], "2": ["id", "guid"] } }
  ]
}
```

- `connection_string`: строка подключения ODBC без логина и пароля. Драйвер в примере подставляется из установленных. Если в строке нет `APP`, скрипт дописывает имя программы: `CompareQuery` для рабочего подключения и `CompareQuery control` для контрольного. По нему администратор видит, чьи это сессии.
- `login`, `password`: дописываются к строке как `UID=...;PWD={...}`. Пароль может содержать любые символы. Если `login` пустой, это вход Windows: к строке дописывается `Trusted_Connection=yes`, если в ней нет `Trusted_Connection`, `Authentication`, `UID` и `PWD` (с ними строка берется как есть). Если в строке уже есть `UID` или `PWD`, а `login` задан, это ошибка.
- `ignored_columns`: игнорируемые колонки. Группа применяется, если `mask` подходит к имени SQL-файла без папки и расширения (`*` и `?`, без учета регистра). В `tables` ключ — номер результирующей таблицы или `*` для всех таблиц, значение — список колонок. Если подходят несколько групп, их колонки объединяются. Колонки, которых нет в таблице, пропускаются. Старый формат с `"columns"` не принимается: скрипт сообщит, как его переделать.

Игнорируемая колонка:

- уходит в конец порядка подбора ключа (см. «Ключ»): по ней сортируются строки, только если без нее ключ не уникален;
- **полностью исключается из сравнения**: строки, которые отличаются только в игнорируемых колонках, считаются одинаковыми. Хэш таблицы считается без них.

Это нужно для колонок, которые отличаются от запуска к запуску: `id` из `identity`, время создания, `newid()`. Номер таблицы — сквозной номер в отчете. Если в запросе добавится или пропадет таблица, номера сдвинутся, и настройку нужно поправить.

Ключи JSON и имена колонок регистронезависимы.

**Пароль хранится в открытом виде.** Не кладите `CompareQuery.json` в систему контроля версий. Строка подключения и пароль никуда не выводятся.

## Режим 1: выполнение запроса

```
python CompareQuery.py query.sql
python CompareQuery.py query.sql --rollback
python CompareQuery.py query.sql --repeat 5
python CompareQuery.py query.sql --profile
```

- Без `--rollback` запрос выполняется без транзакции (autocommit): скрипт ничего не открывает и не держит блокировок сверх того, что делает сам запрос. Изменения данных, если запрос их делает, сохраняются.
- С `--rollback` все батчи выполняются в одной транзакции, в конце делается `rollback`. Подходит для запросов, которые меняют данные, если менять базу нельзя. Это единственный режим скрипта, который заметно влияет на других пользователей: открытая транзакция держит блокировки до конца прогона и не дает очищать журнал транзакций, поэтому он растет. Используйте его для коротких запросов.
- `--repeat N` выполняет запрос N раз, N не меньше 2. Каждый прогон идет на новых подключениях, поэтому `#temp`-таблицы и `SET`-настройки не переходят из прогона в прогон. С `--rollback` откат делается после каждого прогона. Без `--rollback` изменения данных каждого прогона сохраняются, скрипт об этом не предупреждает. Подробнее в разделе «Повторы».
- `--profile` собирает реестр операторов по времени, см. «Реестр операторов».
- `--explain [МС]` (только PostgreSQL, включает `--profile`) — фактические планы операторов не короче МС мс (без числа — все), см. «PostgreSQL».

SQL-файл должен иметь расширение `.sql`. Кодировка определяется автоматически: BOM, затем UTF-8, затем cp1251. Строка, состоящая только из `GO` (можно с пробелами и комментарием), разделяет батчи. `GO 5` не поддерживается. Все батчи прогона идут на одном соединении, поэтому `#temp`-таблицы доступны в следующих батчах.

### Что создается

Рядом с SQL-файлом создается только отчет. Остальное складывается в подпапку с именем SQL-файла без расширения (для `query.sql` — `query`), общую для всех запусков этого файла. Отметка времени одна на весь запуск: `<имя скрипта>_<время>` — имя запуска, с него начинаются имена всех его файлов, номер таблицы стоит после него.

| Файл | Содержимое |
|---|---|
| `query_20261110_153000.txt` | Отчет. В консоль выводится тот же текст без раздела «Производительность». |
| `query/query_20261110_153000_1.csv`, `query/query_20261110_153000_2.csv` | По файлу на каждую результирующую таблицу, нумерация сквозная по всем батчам. С `--repeat` данные сохраняются только из последнего прогона. |
| `query/query_20261110_153000_profile/` | Только с `--profile`: реестр операторов, тексты операторов и планы. |
| `query/query_20261110_153000_message.txt` | Журнал запуска: строки хода выполнения и сообщения SQL (`PRINT`, `RAISERROR`, ошибки, см. ниже) с временем сервера — то же, что видно в консоли. Его показывает итог запуска в окне. |

**Время — по часам сервера**: в отчете («Дата выполнения»), в именах файлов, в реестре и журнале операторов, у сообщений SQL, в `--session`. Часы сервера измеряются один раз при подключении (`SYSDATETIME()` в том же запросе, что и `@@SPID`, — лишнего запроса нет), дальше считаются по часам компьютера. Если часы компьютера отличаются от сервера больше чем на минуту (например, другой часовой пояс), в отчете есть строка «Часы компьютера». Исключение — файлы сравнения (режим 2): там сервера нет, время компьютера.

**Сообщения SQL** выводятся в консоль по ходу выполнения, с временем сервера:

```
[10:15:32.123] Начало расчета
[10:15:40.871] Шаг 1 готов: 30000 строк
```

Показываются `PRINT`, `RAISERROR` с текстом и пользовательские сообщения (номер от 50000), ошибки. Служебные информационные сообщения сервера («Changed database context», «Null value is eliminated by an aggregate» и т. п.) не показываются. Время — момент, когда сообщение пришло скрипту. Сервер копит вывод `PRINT` в буфере и отправляет его вместе с результатами, поэтому чтобы сообщение пришло сразу, в скрипте нужен `RAISERROR('текст', 0, 1) WITH NOWAIT`. Полный список сообщений сервера, включая служебные, — в отчете, раздел «Производительность». Сообщения служебных батчей (`-- ignore in test`) не выводятся. Показанные сообщения вместе со строками хода выполнения сохраняются в `<запуск>_message.txt` в подпапке данных (строка «Журнал:» в отчете); ошибки там с меткой «Ошибка:», остальные сообщения — «SQL:».

В отчете путь к файлам данных и реестру указан относительно папки отчета, поэтому отчет вместе с подпапкой можно переносить. Отчеты, сделанные до появления подпапки, тоже сравниваются: их файлы данных ищутся рядом с отчетом, как и раньше.

Существующие файлы не перезаписываются: при совпадении имени добавляется `_2`.

Отчет состоит из разделов:

- `# Запуск`: SQL-файл и его sha1, сервер и база, дата, режим, число прогонов (с `--repeat`), путь к реестру (с `--profile`), путь к журналу запуска (`Журнал:`).
- `# Сводка`: время, ожидание клиента, CPU, логические и физические чтения, записи за весь запуск, общее время запуска (по часам скрипта, со всеми накладными расходами), сколько всего строк и сколько строк в каждой таблице. С `--repeat` еще время каждого прогона и недетерминированные таблицы.
- `# Таблица N`: файл, число строк, затраты до таблицы, хэш таблицы, хэши колонок, игнорируемые колонки (если есть), приблизительный `create table`, ключ.
- `# Производительность`: время каждого вызова драйвера (execute, получение каждой таблицы, nextset), `rowcount` операторов без результата, время обработки скриптом, все сообщения сервера (`PRINT`, предупреждения, служебные) как есть. С `--repeat` — для последнего прогона. Только в файле: в консоль этот раздел не выводится, его бывает очень много.
- `# Предложение для настроек`: только при `--repeat 2`, см. «Повторы».

**Затраты до таблицы** — время, ожидание клиента, CPU, логические и физические чтения рабочей сессии с конца получения предыдущей таблицы (у первой таблицы — с начала первого батча) до конца получения этой. В них входят операторы без результата, выполненные между двумя таблицами.

Запрос, который не вернул ни одной таблицы, штатный случай: в отчете будет «таблиц нет».

### Контрольное подключение

Время, CPU и чтения меряются со второго, контрольного подключения:

1. Открывается рабочее подключение, скрипт узнает номер его сессии (`@@SPID`). Затем открывается контрольное.
2. Перед каждым батчем контрольное читает счетчики рабочей сессии (`sys.dm_exec_sessions`) и ее ожидание клиента (`sys.dm_exec_session_wait_stats`).
3. Когда таблица получена полностью, контрольное читает счетчики текущего запроса рабочей сессии (`sys.dm_exec_requests`). Разница с предыдущим замером — затраты до таблицы.
4. После батча контрольное читает счетчики еще раз.
5. В конце прогона закрываются оба подключения.

Замеры идут из другой сессии и в рабочей ничего не меняют. `SET STATISTICS IO/TIME` скрипт не включает: на запросах со скалярными функциями `SET STATISTICS TIME` увеличивает CPU самого запроса в разы.

**Время** — время между замерами по часам скрипта минус ожидание клиента: сколько сервер ждал, пока клиент заберет строки результата (`ASYNC_NETWORK_IO`). В это ожидание входят передача результатов по сети и работа самого скрипта с полученными строками, поэтому они во время не попадают. Блокировки, чтение с диска, очередь к процессору и прочие ожидания сервера во время входят: это реальная цена запроса. Ожидание клиента показано отдельно. `sys.dm_exec_session_wait_stats` есть с SQL Server 2016; на более старом сервере будет `Ожидание клиента: нет данных`, и время его включает.

Чтобы контрольное подключение видело рабочую сессию, нужно право `VIEW SERVER STATE` (даже для того же логина). Если права нет или контрольное подключение не открылось, запуск идет дальше без счетчиков: в сводке будет `Счетчики сервера: нет данных (причина)`, строк «Затраты до таблицы» не будет.

### Повторы (`--repeat N`)

Первый прогон — прогрев (кэш данных и планов). Счетчики в отчете — медиана прогонов со второго по последний. Если прогонов два, это просто значения второго прогона. В сводке есть строка `Время по прогонам: ...` по всем прогонам, включая первый.

Если у таблицы в разных прогонах различается число строк или хэш (без игнорируемых колонок), она попадает в строку `Недетерминированные таблицы: ...`. Такую таблицу бессмысленно сравнивать между запусками без настройки `ignored_columns` или правки запроса.

При `--repeat 2` (ровно два прогона) в конце отчета есть раздел `# Предложение для настроек`: готовый элемент для `ignored_columns`, где перечислены все колонки, хэш которых различается между прогонами. Маска — имя SQL-файла (символ `[` экранируется как `[[]`). Текущие настройки при этом не учитываются: если колонка уже игнорируется, но различается, она тоже попадет в список. Таблицы, у которых различается число строк, в элемент не включаются, о них отдельная строка: игнорирование колонок им не поможет. Если запуск прерван, раздела нет.

```
# Предложение для настроек
Колонки, хэш которых различается между прогонами 1 и 2 (текущие настройки не учитываются).
Элемент для ignored_columns в CompareQuery.json:
{"mask": "query", "tables": {"1": ["CreatedAt"], "3": ["id", "ts"]}}
Таблица 2: число строк различается (10 и 11), игнорирование колонок не поможет
```

### Реестр операторов (`--profile`)

Показывает, какие операторы запроса выполняются дольше всего и на что уходит их время, чтобы смотреть их планы в первую очередь.

Пока идет запрос, контрольное подключение раз в 100 мс читает из `sys.dm_exec_requests` текущий оператор рабочей сессии и ее счетчики (выборка). Приращение времени, CPU и чтений между двумя такими выборками относится к оператору второй выборки. Время интервала без CPU — ожидание; оно относится к типу ожидания, который был у запроса в момент выборки (см. ниже). Получается статистическая картина: операторы, которые суммарно работают меньше полсекунды, видны неточно, а верхние операторы долгого запроса — хорошо.

Функции в реестр не попадают. Если выборка попала внутрь функции, ее приращение относится к последнему оператору вне функций в этом же батче: функцию вызвал он. Если такого оператора еще не было, приращение относится к следующему. После выборки внутри функции следующая делается через 30 мс, а не через 100. Встроенные (inline) функции и так часть запроса.

Выборка сделана максимально легкой: два маленьких запроса по одной сессии — строка ее запроса и отдельно проверка, ждет ли кто-то эту сессию. Тексты операторов, имена объектов и планы запрашиваются в отдельном потоке на отдельном подключении: ответ на такие запросы бывает долгим, и выборки его не ждут. Выборка, текст которой еще не получен, ждет его в очереди и учитывается позже, порядок не нарушается.

Если сервер ответил на запрос выборки (строка запроса сессии со временем и счетчиками) дольше 80 мс (`SAMPLE_SLOW_MS`), это задержка: выборка запоздала, и время интервала досталось одному оператору с меньшей точностью. В шапке `registry.txt` есть строка `Задержки выборки (ответ дольше 80 мс): N, всего M мс` — число таких ответов и их суммарная длительность. Вспомогательные запросы (кто ждет сессию, тексты и планы) и ожидание подключения, занятого замером счетчиков, сюда не входят: они не влияют на выборки. В `--profile` время ответа включает и ожидание, пока контрольное подключение снимет счетчики после таблицы (они идут по одному подключению).

Папка `query/query_<время>_profile`:

- `registry.txt` — шапка: число выборок, сколько из них внутри функций, сколько времени распределено по операторам из времени по счетчикам сессии.
- `registry.csv` — таблица операторов по убыванию времени: номер, колонки ниже, логические и физические чтения, число выборок, число запусков, объект (процедура, триггер или SQL-файл), строка в объекте, хэш текста оператора, имена файлов, начало текста оператора.
  - `Запусков` — сколько раз оператор начинал выполняться заново: возврат к нему после другого оператора (цикл, повторный вызов процедуры) или новый запрос с ним. Помогает понять, долго ли оператор выполнялся один раз или это много коротких запусков. Выборки внутри функций выполнение не прерывают (как в журнале), поэтому мерцание «вызывающий оператор — оператор функции» счетчик не увеличивает. Это нижняя оценка: повторы, между которыми выборка не застала другого оператора, не видны. С `--repeat` — медиана прогонов.
  - `Хэш` — контрольная сумма текста оператора без учета пробелов и регистра. По нему режим 2 находит тот же оператор в другом запуске: номер строки сдвигается при любой правке процедуры, а текст оператора нет. Он же отличает разные операторы на одной строке.
  - `Начало текста` — первые 100 символов (`REGISTRY_TEXT_LEN`) как есть, кроме переводов строк и управляющих символов, ломающих строку CSV: они заменены пробелами (`\r\n` — одним). Табуляция остается табуляцией, поэтому кусок можно скопировать и найти поиском в исходном тексте, если он не переходит через перевод строки.
- `log.csv` — журнал выполнения, см. ниже.
- `NNN - T.sql` — текст оператора с номером NNN, T — его время в мс (например, `001 - 15155.sql`). В первых двух строках комментарии: объект и строка, затем значения из реестра: `--Время мс: 15155; CPU мс: 9180; ...` — те же значения, что в колонках реестра, кроме пустых, доли и ожидания клиента.
- `NNN - T.sqlplan` — план оператора из кэша планов, для первых 30 операторов. Открывается в SSMS. Это план без фактических значений (число строк по оценке), фактический план так не получить без изменения настроек базы.

Колонки реестра:

| Колонка | Смысл |
|---|---|
| `Время мс`, `Время %` | время выполнения без ожидания клиента; доля от времени запуска по счетчикам сессии |
| `CPU мс` | CPU; у параллельных планов бывает больше времени |
| `Ожидание блокировок мс` | ожидание блокировок (`LCK_M_*`), которые держат другие сессии |
| `Блокировал сам мс` | время, когда хотя бы одна другая сессия ждала блокировку этой сессии. Сколько их и есть ли цепочки, не важно |
| `Ожидание ресурсов мс` | остальные ожидания сервера: диск, память, процессор, параллелизм и прочее |
| `Ожидание ресурсов 1/2/3 место` | три самых долгих типа из предыдущей колонки: `PAGEIOLATCH_* (1234 мс)` |
| `Выделено памяти МБ` | наибольшее выделение памяти запросу (`granted_query_memory`), которое встретилось в выборках |
| `Ожидание клиента мс` | `ASYNC_NETWORK_IO`: сервер ждал, пока клиент заберет строки. Во время не входит |

Тип ожидания берется из выборки: текущий (`wait_type`); если запрос ждет процессор (`runnable`) — `SOS_SCHEDULER_YIELD`; если выполняется — последний завершенный (`last_wait_type`). Подтипы `PAGEIOLATCH_*`, `PAGELATCH_*` и `LATCH_*` объединяются: суть у них одна. Все это приблизительно, с точностью до интервала выборки: если за 100 мс запрос успел подождать разного, все ожидание интервала достанется одному типу. «Блокировал сам» считается целыми интервалами.

Блокировки, которые держит транзакция с `--rollback` после окончания оператора, тоже видны, но относятся к оператору, который выполняется в этот момент. Между батчами выборок нет.

Оператор определяется объектом, строкой и хэшем текста. Если он выполняется несколько раз (в цикле, при нескольких вызовах процедуры, `GO N`), значения по всем выполнениям суммируются в одну строку реестра.

С `--repeat` значения реестра — медиана прогонов со второго по последний. Строка у операторов SQL-файла — строка в самом файле, у процедур — строка от начала текста процедуры, как в сообщениях об ошибках SQL Server.

**Журнал `log.csv`** — те же колонки, но строка — не оператор за весь запуск, а одно непрерывное выполнение оператора: от первой выборки, где он появился, до выборки, где начался другой оператор или запрос закончился. Выборки внутри функций выполнение не прерывают. Выборка, у которой текст оператора не длиннее 2 символов, считается ошибочной (сервер отдал границы оператора в момент его смены) и обрабатывается как выборка внутри функции: относится к предыдущему оператору, следующий опрос идет сразу. В `--session` запрос, начавшийся до наблюдения, в первой выборке дает нулевое время: его прежние затраты относятся к неизвестным операторам, а не к оператору первой строки журнала. Строки идут в порядке появления, старые не меняются. Один и тот же оператор (например, в цикле) встречается много раз. Вместо номера первая колонка — время сервера начала выполнения (с точностью до интервала выборки; у первого оператора батча — время начала батча). Колонок `Время %`, `Хэш`, `Текст`, `План` и `Запусков` (строка журнала — один запуск) в журнале нет: номера файлов NNN меняются вместе с порядком операторов, а журнал только дописывается (в `--session` — по ходу наблюдения), поэтому журналы `--profile` и `--session` одинаковые. Оператор журнала находится в реестре по объекту и строке, при сомнении — по началу текста. С `--repeat` в журнале все прогоны со второго.

Чего реестр не дает: числа выполнений оператора и времени процедуры вместе с вложенными вызовами. Выборка видит только самый внутренний оператор, поэтому у процедуры считается время ее собственных операторов.

### Нагрузка на сервер

Скрипт ничего не создает и не меняет на сервере: ни объектов, ни настроек, ни файлов. Кэш планов и буферов не очищается. Все, что он делает сверх вашего запроса, — чтения служебных представлений:

| Что | Когда | Нагрузка |
|---|---|---|
| счетчики сессии и запроса | перед каждым батчем, после каждой таблицы и батча | одна строка из `sys.dm_exec_sessions`/`requests` |
| текущий оператор | `--profile`, `--session`: 10 раз в секунду (до 33 внутри функций) | два запроса: одна строка из `sys.dm_exec_requests` по сессии и проверка, ждет ли кто-то эту сессию |
| текст операторов и объекты | `--profile`, `--session`: один раз на модуль, в отдельном потоке и подключении | `sys.dm_exec_sql_text`, имя и тип объекта |
| планы | `--profile`: в конце, для 30 операторов; `--session`: при обновлении файлов, для новых операторов из первых 30, в отдельном потоке | `sys.dm_exec_text_query_plan` |
| сессия жива | `--session`: раз в секунду | одна строка из `sys.dm_exec_sessions` |

Сознательно не используются: Extended Events (серверный объект и затраты на каждый вызов функции), `sys.dm_exec_query_statistics_xml` (известные сбои сервера при частом опросе), `sys.dm_exec_query_stats` (чтение всего кэша планов, данные смешаны с чужими запросами), `SET STATISTICS IO/TIME`.

Нагрузку задают сам запрос, `--repeat` (запрос выполняется N раз) и `--rollback` (см. выше).

### Служебные батчи (`--ignore in test`)

Если первая непустая строка батча — комментарий `--ignore in test` (регистр и пробелы после `--` не важны), батч выполняется как обычно (с `--rollback` откатывается вместе с остальными), но в отчет ничего из него не попадает:

- его таблицы читаются и отбрасываются, нумерация таблиц их пропускает: таблицы остальных батчей получают те же номера, что и в запросе без служебных батчей, поэтому такие запуски сравниваются с обычными;
- его время, CPU и чтения не входят ни в сводку, ни в «Затраты до таблицы»;
- его операторы (и вызванные из него процедуры) не попадают в реестр и журнал `--profile`;
- его сообщения сервера и время вызовов драйвера не попадают в раздел «Производительность»; там только строка `Батч N: --ignore in test, в отчет не попадает`.

В разделе `# Запуск` есть строка `Игнорируемые батчи (--ignore in test): N`. Такие батчи могут стоять где угодно: в начале (подготовка тестовых данных), в середине или в конце. Ошибка в служебном батче прерывает запуск, как и в обычном.

```
-- ignore in test
insert into #params values (1, '2026-01-01')
GO
exec dbo.CalcSalary
```

### Ошибка во время выполнения

Если сервер вернул ошибку или нажат Ctrl+C, уже полученные таблицы обрабатываются и сохраняются, в отчет пишется `ЗАПУСК ПРЕРВАН: <текст ошибки>`, код возврата 2. Таблица, которая получена не полностью, не сохраняется. С `--repeat` следующие прогоны не выполняются. Если прерван не последний прогон, данных нет: они сохраняются только в последнем. Такие отчеты режим 2 не принимает.

Ctrl+C срабатывает, когда драйвер возвращает управление, то есть не посреди долгого `execute` (команда `stop` из другой программы отменяет и долгий оператор, см. «Запуск из другой программы»). После прерванного запуска без `--rollback` открытая скриптом транзакция откатывается (`IF @@TRANCOUNT > 0 ROLLBACK`). Повторный Ctrl+C во время обработки таблиц прерывает скрипт без отчета.

## Режим 3: наблюдение за сессией (`--session N`)

```
python CompareQuery.py --session 87
```

Собирает реестр операторов чужой сессии с номером N (его видно в SSMS, Activity Monitor, `sp_who2`): то же, что `--profile`, но запрос выполняет не скрипт, а кто-то другой. Скрипт ничего не выполняет в этой сессии, только читает служебные представления со своих двух подключений (выборки и, отдельно, тексты и планы). Нужно право `VIEW SERVER STATE` (как это устроено у PostgreSQL — в разделе «PostgreSQL»). План оператора появляется в папке при одном из следующих обновлений файлов: он запрашивается в отдельном потоке.

Результат — папка `Sessions_profile\Session_<время>_N` в текущей папке (или в `OUTPUT_DIR`; время — начало наблюдения по часам сервера) с теми же файлами, что у `--profile`: `registry.txt`, `registry.csv`, `log.csv`, `NNN - T.sql`, `NNN - T.sqlplan`. Время в шапке — сумма по выборкам, доля считается от нее. В шапке есть и «Исходный запрос» — последний батч, который прислал клиент (часто вызов процедуры с параметрами), одной строкой; он обновляется при каждой записи файлов.

- Файлы реестра обновляются раз в 10 секунд (`SESSION_FLUSH_S`): порядок операторов, номера и время в именах файлов и планы меняются по ходу. Каждый файл пишется через временный и подменяется целиком, поэтому скрипт можно закрыть в любой момент: на диске останется последнее полное состояние, не старше 10 секунд.
- Лишней записи нет: неизменившийся файл не трогается; файл, у которого изменилось только имя (номер или время, а текст тот же — обычно это план и тексты операторов, которые сейчас не выполняются), переименовывается; заново пишутся только новые и изменившиеся (`registry.csv`, `registry.txt`, тексты выполняющихся операторов — у них в комментарии растет время). План получается с сервера один раз.
- `log.csv` дописывается сразу, как закончилось выполнение оператора, без ожидания 10 секунд.
- Если файл открыт в другой программе (Excel блокирует открытый файл), он пропускается до следующего раза, о чем выводится одно сообщение. Строки журнала в этом случае ждут в памяти.
- В консоли строки до 79 символов: время сервера, когда оператор впервые попал в выборку, объект и строка, начало текста (30 символов), текущее ожидание (если запрос ждет другую сессию — с ее номером: `LCK_M_U ждет 112`). Пока выполняется тот же оператор, строка обновляется на месте и только когда в ней что-то изменилось (например, ожидание); начался другой оператор или запрос — новая строка, так в консоли видно, как шла процедура. Пока сессия ничего не выполняет — `нет запроса`.

```
10:12:34 dbo.CalcSalary:154 update s set Amount = r.Rate * s.H LCK_M_U
```

Выход:

- любая клавиша (в консоли Windows), Ctrl+C или команда `stop` (см. «Запуск из другой программы»). Если в этот момент пишутся файлы, запись доделывается. Затем файлы записываются последний раз (только на диск, без запросов к серверу) и скрипт завершается;
- сессия N завершилась (или ее номер получила другая сессия: проверяется время подключения);
- ошибка подключения: код возврата 2, данные до этого момента сохранены.

Пока сессия простаивает между запросами, выборок нет. Сравнение двух отчетов (режим 2) для `--session` не предусмотрено: отчета запуска нет, только папка реестра.

## Режим 2: сравнение двух запусков

```
python CompareQuery.py query_20261110_153000.txt query_20261111_090000.txt
```

Аргументы — два отчета режима 1: первый A (обычно образец), второй B (обычно проверяемый запуск). Файлы данных ищутся по путям из отчетов, относительно папки отчета. Рядом с отчетом B создаются два файла:

- `<отчетB>__<отчетA>_compare_<время>.txt` — полный отчет;
- `<отчетB>__<отчетA>_compare_<время>_short.txt` — сокращенный отчет, тот же текст выводится в консоль.

Имя начинается с отчета B, поэтому при сортировке по имени сравнение стоит сразу за проверяемым отчетом.

Чем сокращенный отчет отличается от полного:

- в заголовке только имена двух отчетов, без sha1 SQL-файлов, сервера и режима;
- нет предупреждения о разных SQL-файлах и напоминания о сравнении без учета регистра;
- ключ показан списком колонок. Если ключи двух запусков различаются, они показаны отдельно для A и для B;
- нет строки о совпавших хэшах (это видно по заголовку «идентична») и предупреждений о разных типах внутри одного семейства;
- строки «Строк только в A/B» и «Сопоставлено строк» опускаются, если в них 0;
- в разделе операторов не больше 10 строк.

Затраты показаны в заголовке за весь запуск и для каждой таблицы: `Затраты до таблицы: время A=1500 B=1100 мс (-27%), CPU A=120 B=100 мс (-17%), чтений A=4500 B=4400 (-2%)`. Время — без ожидания клиента, как в отчете запуска. Чтения здесь — логические: физические зависят от того, что было в кэше, и для сравнения не годятся. У отчетов, сделанных до появления времени, будет `время нет данных`.

Таблицы сопоставляются по номеру. Для каждой таблицы проверяется:

1. **Структура**: число, имена и порядок колонок. Если структура различается, строки не сравниваются, но число строк и хэши общих колонок сравниваются. Разные типы одного семейства (число, строка, дата, байты) дают только предупреждение.
2. **Ключи**. Совместимы, если один ключ — начало другого (например, `(acsId)` и `(acsId, proId)`): тогда файлы читаются потоком, без загрузки в память. Иначе (данные изменились так, что ключ подобрался другой, или различаются настройки `ignored_columns`) таблицы сравниваются в памяти, см. ниже.
3. **Хэши**: если совпали число строк, хэш таблицы и хэши всех колонок, таблица идентична, данные не читаются.
4. **Построчное сравнение** обоих отсортированных файлов. В отчете будет: сколько строк есть только в A и только в B, сколько сопоставлено и сколько из них отличается, какие колонки отличаются, примеры.

**Сравнение в памяти** при разных ключах: обе таблицы загружаются целиком, сортируются по общему ключу и сравниваются так же. Общий ключ — ключ A, если он уникален в обоих запусках, иначе ключ B, иначе объединение обоих ключей (оно уникально в обоих запусках). Игнорируемые колонки и `#dup` в общий ключ не входят. В отчете это строки `ключи различаются, таблицы сравниваются в памяти` и `Сопоставление в памяти по (...)`. Например, A подобрал ключ `(acsId)`, а B, где у одной строки изменился `hhId`, подобрал `(id, hhId)`. Тогда сопоставление идет по `acsId`, и изменение видно как отличие в `hhId`, а не как пара «только в A» и «только в B». Памяти на такую таблицу нужно примерно вдвое больше, чем при ее обработке в режиме 1: держатся обе стороны.

**Значения сравниваются без учета регистра**: `Abc` и `ABC` считаются одинаковыми. В файлах данных значения хранятся как есть.

**Игнорируемые колонки** берутся из отчетов, а не из текущих настроек: в сравнении не участвуют колонки, игнорируемые хотя бы в одном из двух запусков. Они перечислены в строке `Игнорируемые колонки` таблицы. Если настройки двух запусков различаются, это отмечено в той же строке. Если ключ дошел до игнорируемых колонок (без них строки не уникальны), строки сопоставляются по остальным колонкам с учетом числа повторов.

Если ключ таблицы в одном запуске короче, чем в другом, строки сопоставляются по более короткому ключу. Строки длинной стороны, которые совпали по короткому ключу и остались без пары, показываются отдельным счетчиком как «лишние дубликаты по короткому ключу».

Если файл данных не найден, его заголовок не совпадает с колонками отчета или файл изменен (нарушен порядок строк, другое число строк), это написано в отчете. Нарушение порядка считается ошибкой сравнения, код возврата 2.

### Сравнение реестров операторов

Если оба запуска были с `--profile`, после заголовка идет раздел `# Операторы: значимые изменения времени`:

```
# Операторы: значимые изменения времени (от 20% и 1000 мс)
dbo.CalcSalary, стр. 154: 9230 -> 2210 мс (-76%), CPU 5230 -> 1210, чтений 1200000 -> 3000
dbo.LoadRates, стр. 40 (текст изменен): 500 -> 2900 мс (+480%), CPU 300 -> 1900, чтений 900 -> 52000
```

- Операторы сопоставляются по объекту и хэшу текста, а не по номеру строки: строки сдвигаются при любой правке процедуры. Одинаковые операторы одного объекта сопоставляются по порядку; переставленные местами неизмененные операторы тоже находятся.
- Переименованная копия процедуры или скрипта (`PrintNewPD` → `PrintNewPDTest`, `q.sql` → `q_Test.sql`) узнается по одинаковым операторам: если у объекта A и объекта B с другим именем не меньше 3 общих операторов (хэш встречается по одному разу в каждом запуске) и это больше половины таких операторов объекта A, они считаются одним объектом. В отчете строка «Объект A … сопоставлен с объектом B … (N одинаковых операторов)».
- Оператор с измененным текстом (добавили хинт, колонку, join) ищется в своем промежутке: совпавшие по хэшу операторы того же объекта служат опорными точками, и оператор между двумя соседними опорными в A сопоставляется с оператором между теми же опорными в B. Поэтому сдвиг строк (вставили строки выше) не мешает, а оператор не может «перепрыгнуть» через неизмененный. В промежутке сначала пара по первым 20 символам текста (без учета пробелов и регистра), если по ним пара однозначна, затем пара на одной строке. «По порядку» не сопоставляется: на реальных реестрах это склеивало разные операторы. Такие пары помечаются «(текст изменен)», остальные — «(нет в A)» или «(нет в B)». Если строка оператора в A другая, она указана в пометке: «(текст изменен, в A стр. 38)». Ошибиться так можно, только если в одном промежутке переписали несколько операторов с одинаковым началом текста — тогда пары нет, а не неверная пара. В реестр попадают только операторы, которые застала выборка, поэтому быстрый оператор может оказаться только в одном из запусков.
- Рассматриваются только операторы из верхних 20% по времени, но не меньше 5, в A или в B.
- Значимое изменение — не меньше 20% и не меньше 1000 мс времени. Показываются и ускорения, и замедления, по убыванию изменения.

Если реестр есть только у одного запуска или файл реестра не найден, в разделе будет об этом строка. Таблица операторов берется из `registry.csv`, а у реестров, сделанных до его появления, — из `registry.txt`.

### Сравнение двух наблюдений (двух реестров)

```
python CompareQuery.py Sessions_profile\Session_A Sessions_profile\Session_B
```

Если оба аргумента — папки реестров (наблюдения `--session` или реестры `--profile`) или их `registry.txt`, сравниваются только операторы, без таблиц. Отчет с папкой смешивать нельзя. Файлы `<B>__<A>_compare_<время>.txt` и `_short.txt` пишутся рядом с папкой B. Порядок выполнения в сравнении не используется: подключение посреди процесса, циклы и перестановки на сопоставление не влияют (оно то же, что выше, и идет по строкам текста процедуры).
- **Позднее подключение.** По `log.csv` берется самый ранний оператор, который застало позднее наблюдение и который есть в обоих. Операторы другого наблюдения, которые выполнялись только раньше его первого выполнения и которых нет в позднем, не учитываются: строка «Наблюдение B началось позже: не учитываются операторы A (N), выполненные только до …», список — в полном отчете. В цикле берется первое выполнение, поэтому исключается скорее меньше, чем больше. Первый оператор каждого наблюдения отмечен: его начало могло пройти до подключения. Нет `log.csv` — начало не выравнивается, об этом строка в отчете.
- **Циклы.** У операторов со значимым изменением показано число запусков и время на запуск: «запусков 100 -> 60 (на запуск 40 -> 41 мс)» — время упало из-за числа итераций, а не из-за оператора. Число запусков — нижняя оценка (повторы между двумя выборками не видны).
- **Объекты.** Время по объектам (переименованная копия — под именем B): в полном отчете все, в сокращенном — значимые изменения. Это работает и когда внутри объекта другой алгоритм и операторы не совпадают.

## PostgreSQL

Скрипт работает и с PostgreSQL: какая СУБД, он понимает по строке подключения. Строка libpq — `host=... port=... dbname=...` или `postgresql://host:port/база` — значит PostgreSQL, строка ODBC (`Driver=...;Server=...`) — MS SQL Server. Все остальное — команды, отчеты, сравнение, GUI — одинаково.

```json
{
  "connection_string": "host=db1 port=5432 dbname=app sslmode=prefer",
  "login": "tester",
  "password": "..."
}
```

- Нужен модуль psycopg: `pip install "psycopg[binary]"` (драйвер PostgreSQL внутри, ставить отдельно ничего не нужно). Лаунчер ставит его вместе с остальными пакетами.
- `login` и `password` передаются отдельно от строки. Если `login` пустой, берутся пользователь и пароль из самой строки, из `PGUSER`/`PGPASSWORD` или из файла `pgpass.conf` — как у любой программы на libpq. Если в строке уже есть `user` или `password`, а `login` задан, это ошибка.
- Имя программы (`application_name`) — как у MS SQL Server: `CompareQuery`, `CompareQuery control` и т. д., если в строке его нет.
- **Операторы.** Файл делится на операторы по `;` (вне строк, комментариев и тел функций в `$$...$$`), каждый оператор — свой «батч»: отдельный вызов к серверу, свой номер в журнале, свой результат. `-- ignore in test` ставится строкой над оператором. Команды psql (`\i`, `\set`, `COPY ... FROM STDIN`) не поддерживаются.
- **Транзакции.** Без `--rollback` — autocommit, как у MS SQL Server. С `--rollback` весь прогон — одна транзакция, которую скрипт откатывает; поэтому `BEGIN`, `COMMIT`, `ROLLBACK` в самом файле с `--rollback` запрещены (скрипт скажет, в какой строке). Если запуск прервался внутри транзакции, открытой файлом (`BEGIN`), скрипт ее откатывает. В PostgreSQL ошибка внутри транзакции прерывает ее целиком.
- **Типы.** Числа, строки, `bool`, даты и время, `uuid`, `bytea` читаются как значения и дают тот же канонический текст, что у MS SQL Server: одинаковые данные из двух СУБД дают одинаковые хэши, и запуски на MS SQL Server и PostgreSQL можно сравнивать (`bool` = `bit`: `1`/`0`; `timestamptz` = `datetimeoffset`: время UTC с `Z`). Остальные типы (`json`, массивы, `interval`, `inet`, `money`, `timetz`, диапазоны, перечисления) идут текстом, как их выводит сервер. `'infinity'` и `'-infinity'` в датах становятся `9999-12-31...` и `0001-01-01...` (в Python нет бесконечной даты). `create table` в отчете — в синтаксисе PostgreSQL с типами сервера (`create temp table t1("id" int4, ...)`), в том числе своими (перечисления, домены); тип, созданный самим SQL-файлом, пишется номером.
- **Результат оператора приходит в память целиком** (в компактном виде драйвера), строки обрабатываются блоками. Сервер не ждет, пока скрипт обработает строки, но результат больше свободной памяти компьютера не поместится.
- **Сообщения** `RAISE NOTICE`, `RAISE WARNING` и уведомления сервера показываются по ходу выполнения, как `PRINT` у MS SQL Server; у предупреждений — пометка `WARNING:`.
- **Счетчики сервера.** Время оператора — по часам сервера, от начала до конца оператора (`pg_stat_activity`); в него входит передача результата клиенту (результат приходит целиком до конца оператора), а работа скрипта со строками — нет. Логические и физические чтения и записи — из расширения `pg_stat_statements`, если оно есть: разница строки запроса (`query_id`, PostgreSQL 14+) до и после оператора; логические — все обращения к буферам (`shared` и `local`, физические в них входят), физические — чтения мимо кэша буферов сервера (их может отдать кэш ОС), записи — `shared`, `local` и временные файлы. `pg_stat_statements` общий для всех сессий: если тот же запрос в это время выполнял кто-то еще, в сводке пометка, что чтения этих операторов завышены. CPU и ожидания клиента по сессии в PostgreSQL нет — в отчете «нет данных» с причиной (не 0, чтобы сравнение не показывало «CPU −100%»). Без `pg_stat_statements` (или на PostgreSQL до 14) чтения тоже «нет данных».
- **`--profile`** — реестр по операторам SQL-файла (у PostgreSQL виден только оператор верхнего уровня, операторы внутри функций не видны). Раз в 100 мс читается состояние рабочей сессии в `pg_stat_activity`, и время оператора раскладывается по ожиданиям: `Lock` — «Ожидание блокировок» (кто держит — номер сессии в событиях и строке состояния), `Client` — «Ожидание клиента», прочее — «Ожидание ресурсов» с типом (`IO:DataFileRead`, `Timeout:PgSleep`, `LWLock:...`). «CPU мс» — оценка: время выборок, в которых оператор ничего не ждал. «Блокировал сам мс» — время, пока другая сессия ждала блокировку этого оператора. У параллельного плана, пока оператор ждет процессы-помощники (`IPC:ExecuteGather` и т. п.), выборка относится к их самому частому ожиданию (`IO:DataFileRead`, `CPU`…): видно, чем заняты помощники. Время и чтения оператора — точные (из счетчиков выше), поэтому в реестр попадают и операторы короче интервала выборки, только без разбивки по ожиданиям. «Выделено памяти МБ» у PostgreSQL пусто.
- **Функции и таблицы** (`--profile`): в папке реестра `functions.csv` — вызовов, время с вложенными функциями и собственное время каждой функции, и `tables.csv` — просмотров таблицы (`seq scan`, `index scan`) и прочитанных ими строк, вставлено, изменено, удалено. Для функций скрипт включает `track_functions = 'all'` на своем подключении (нужны права суперпользователя или право на этот параметр; без них — то, что включено на сервере, или «нет данных» с причиной). С `--rollback` это счетчики своей транзакции (`pg_stat_xact_*`) — только операторы скрипта. Без `--rollback` — разница общей статистики сервера до и после прогона: в нее входит работа других сессий с теми же функциями и таблицами, а временные таблицы скрипта к этому моменту уже удалены.
- **Планы (`--explain [МС]`)** — фактические планы (время и строки каждого шага, буферы). Включает `--profile`; МС — порог: план пишется для операторов не короче МС мс (без числа — для всех; у функции, которую вызывают миллион раз, будет миллион планов, поэтому для таких скриптов порог лучше задать). Способ выбирается сам:
  - **`auto_explain`** (нужны права суперпользователя): модуль подгружается только в свое подключение (`LOAD`, на сервер ничего не ставится), планы приходят скрипту сообщениями и в журнал сервера не пишутся. План оператора — в колонке «План» реестра (`NNN - T.txt`). Операторы **внутри функций** — в `nested.csv`: функция, строка в ее теле (считается от начала тела, после `$$`), вызовов, время (с вложенными вызовами), наибольшее время, чтения, план самого долгого вызова (`nNNN - T.txt`). Сервер замеряет каждый шаг плана, поэтому время такого запуска завышено: в отчете строка «Планы (--explain)», а сравнение с запуском без нее предупреждает, что время может быть несравнимо.
  - **Без прав, с `--rollback`** — после измеряемых прогонов отдельный прогон: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `VALUES`, `TABLE`, `WITH` выполняются как `EXPLAIN (ANALYZE, BUFFERS)`, остальное (`CREATE`, служебные батчи) — как есть, все в одной транзакции с откатом. Планы — только операторов верхнего уровня, время измеряемых прогонов не меняется.
  - **Без прав и без `--rollback`** — планов нет (в реестре «нет данных» с причиной): отдельный прогон выполнил бы изменения данных второй раз.
- **Наблюдение `--session N`** (N — `pid` сессии из `pg_stat_activity`, `--show sessions` или GUI). Одно подключение: раз в 100 мс одна строка этой сессии из `pg_stat_activity` (и, пока оператор выполняется, проверка, ждет ли кто-то его блокировку). Нужна роль `pg_read_all_stats` (входит в `pg_monitor`), суперпользователь или подключение тем же пользователем, что у сессии: иначе сервер скрывает ее запросы, и скрипт об этом скажет. Чем отличается от MS SQL Server:
  - оператор — запрос, который прислал клиент (`pg_stat_activity.query`, обрезан по `track_activity_query_size`); операторов внутри функций не видно, объекта и строки нет (`(батч)`, строка 1). Запросы, отличающиеся только значениями (`select 1`, `select 2`), — разные операторы; с параметрами (`$1`) — один;
  - если после оператора сессия простаивала (в выборку попала строка `idle` или `idle in transaction`), его время точное (`state_change - query_start`), а чтения — разница строки `pg_stat_statements` его `query_id`, как у своего запуска. Если следующий оператор начался до выборки, время — до последней выборки, чтений нет. `pg_stat_statements` общий: если тот же запрос между выборками выполнялся еще раз (этой сессией или другими), в шапке пометка, что чтения таких операторов завышены. Чтения берутся из `pg_stat_statements` той базы, к которой подключен скрипт: нет там расширения — «нет данных»;
  - оператор короче интервала выборки виден, только если после него сессия простаивала (ожидания у него неизвестны), остальные короткие не видны, как у MS SQL Server;
  - CPU — оценка по выборкам без ожидания, ожидания (и процессы-помощники) и «Блокировал сам» — как у `--profile`; фактических планов нет (`auto_explain` в чужую сессию не подгрузить), колонка «План» пустая, оценочный план оператора — в GUI (см. ниже); `functions.csv` и `tables.csv` нет (статистика своей транзакции есть только у своей сессии);
  - нагрузка: на каждый замеченный конец оператора — одно чтение `pg_stat_statements` без текстов запросов, не чаще выборок. Оно перебирает всю статистику запросов сервера под разделяемой блокировкой: другие сессии ждут его, только когда добавляют в статистику новый запрос.
- **Просмотр сервера.** `--show sessions` и `--show current` — из `pg_stat_activity` (кто кого блокирует — `pg_blocking_pids`, только у сессий, которые ждут блокировку: функция ненадолго занимает менеджер блокировок сервера, поэтому не для всех). `--show heavy` — из расширения `pg_stat_statements`, если оно установлено на сервере; показатели — `time` (по умолчанию), `time_avg`, `reads`, `reads_avg`, `writes`, `execs`, `max_time`; `--hours` нет (в `pg_stat_statements` нет времени последнего выполнения). `--cancel N` отменяет текущий запрос сессии (`pg_cancel_backend`), `--kill N` закрывает сессию (`pg_terminate_backend`).
  - `--show heavy --interval S` — разница двух снимков `pg_stat_statements` без текстов запросов (файл текстов читается один раз, для показанных строк): какие запросы нагружали сервер за эти секунды. `max_time` за интервал не считается.
  - `tables` — `pg_stat_user_tables` и `pg_statio_user_tables` текущей базы: прочитано строк (seq scan + index scan), сканирований, вставлено, изменено, удалено, мертвых строк, блоков с диска и из кэша, размер (оценка по `pg_class.relpages`: точный размер встал бы в очередь за `ALTER TABLE`), последний vacuum и analyze.
  - `functions` — `pg_stat_user_functions` текущей базы: вызовов, время, собственное время. Считается только при `track_functions` на сервере (по умолчанию `none` — пометка в конце).
  - `io` — `pg_stat_io` (PostgreSQL 16+): чтения, записи, расширения файлов, попадания в кэш по видам процессов и объектов. Время чтений и записей — только при `track_io_timing = on`, иначе «нет данных».
  - `waits` — накопительных счетчиков ожиданий в PostgreSQL нет, поэтому раз в 100 мс читаются активные клиентские сессии из `pg_stat_activity` (как ASH): выборка, где сессия ждала событие, — 100 мс этого ожидания, без ожидания — `CPU`. Время — оценка; в строке — сколько сессий ждали и самый частый запрос.
  - `space` — размеры баз сервера, свои табличные пространства, папка WAL (число файлов) и слоты репликации (активен ли слот); вид в колонке «Вид»: `db`, `tablespace`, `wal`, `slot`. Свободное место на диске средствами SQL не узнать.
  - `temp` — временные файлы сессий (`pg_ls_tmpdir`, нужна роль `pg_monitor`) и в конце — временные файлы баз с последнего сброса статистики.
- **GUI.** Подстраивается под СУБД подключения: в параметрах запуска есть «Планы (--explain)» с порогом в мс; в итоге запуска под журналом — «Операторы внутри функций», «Функции» и «Таблицы» (если они есть и не пустые); колонки, которых у PostgreSQL нет (память, CPU в «Текущих» и «Тяжелых запросах», время в кэше), не показываются, а плашки «Ждут память» и «Очередь на процессор» показывают «—». «Тяжелые запросы» по умолчанию сортируются по времени, отбора по часам нет: за последние секунды — «Период: замер за 10, 30, 60 с» на экране «Нагрузка сервера».
  - **Отменить запрос** — значок в «Текущих запросах» у выполняющегося запроса: `pg_cancel_backend`, запрос прерывается с ошибкой, сессия остается (KILL закрывает ее совсем). С подтверждением, как KILL.
  - **Оценочный план** — кнопка в окне текста запроса («Текущие запросы», «Нагрузка сервера», текст оператора реестра и наблюдения): `EXPLAIN` без выполнения — план, который построил бы сервер. С PostgreSQL 16 — `GENERIC_PLAN`, поэтому план строится и для текстов с параметрами `$1` (так их показывают `pg_stat_statements` и программы). Выполняется на отдельном подключении только для чтения к базе запроса (для реестра — к базе подключения); нужны права на чтение таблиц запроса. Только один оператор `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `VALUES`, `TABLE` или `WITH`; план открывается файлом `.txt`.
- Служебные подключения (GUI, `--show`) не ждут чужих блокировок дольше 3 с (`lock_timeout`).

## Просмотр сервера (`--show`, `--kill`)

Те же запросы, что в GUI («Новое наблюдение», «Текущие запросы», «Нагрузка сервера»), из консоли:

```
python CompareQuery.py --show sessions
python CompareQuery.py --show current --top 50
python CompareQuery.py --show heavy --order reads --hours 24 --csv heavy.csv
python CompareQuery.py --show waits --interval 30
python CompareQuery.py --show tables --interval 10
python CompareQuery.py --show space
python CompareQuery.py --kill 87
```

- `sessions` — пользовательские сессии: база, логин, компьютер, программа, сколько идет запрос, процедура.
- `current` — текущие запросы и сессии, которые блокируют других: время, CPU, чтения, ожидание, кого ждет, скольких блокирует, оператор; в конце — итоги по серверу.
- `heavy` — тяжелые запросы кэша планов. `--order` — показатель: `cpu` (по умолчанию), `cpu_avg`, `time`, `time_avg`, `reads`, `reads_avg`, `writes`, `execs`, `max_time`; `--hours N` — только выполнявшиеся за последние N часов. Строк запроса — `--top`, но не меньше 100 (как в GUI).
- `tables` — таблицы текущей базы: обращения на чтение (`seek`, `scan`, `lookup` по `sys.dm_db_index_usage_stats`), изменения, число строк (из `sys.partitions`), время последнего чтения и изменения. Сортировка — по обращениям на чтение.
- `functions` — процедуры и функции текущей базы, план которых сейчас в кэше: выполнений, CPU, время, логические чтения (`sys.dm_exec_procedure_stats`, `sys.dm_exec_function_stats` — с SQL Server 2016; на более старом — только процедуры, с пометкой). Сортировка — по времени.
- `io` — файлы всех баз: чтений и записей, мегабайт, ожидание чтения и записи (`sys.dm_io_virtual_file_stats`), путь — в CSV. Сортировка — по общему ожиданию.
- `waits` — ожидания всего сервера за `--interval` секунд (по умолчанию 10): разница двух снимков `sys.dm_os_wait_stats`, без фоновых ожиданий, которые ждут работы, а не мешают ей (`LAZYWRITER_SLEEP`, `XE_TIMER_EVENT` и т. п.). Время, доля, число ожиданий, из них сигнал (очередь к CPU) — в CSV.
- `space` — место базы подключения, как раздел «Место» экрана «База данных»: файлы, размер, занято, свободно в файле, прирост, предел, «можно занять еще» и свободное место на диске (диски — при праве `VIEW SERVER STATE`); в конце — итог по данным и логу.
- `temp` — временные данные всего сервера, как раздел «Временные данные»: сколько каждая сессия занимает в tempdb (пользовательские объекты `#temp`, `@table` и внутренние — сортировки, hash) и запрос; в конце — сводка по tempdb.

**`--interval S`** — два снимка с паузой S секунд и их разница: что происходило на сервере именно за эти секунды, а не с перезапуска сервера. Работает для `tables`, `functions`, `io` (у `space` и `temp` его нет: это не счетчики; без него — накопленные значения, в конце таблицы написано, с какого момента), у `waits` — длительность. Строки, где за интервал ничего не изменилось, не выводятся. Для `heavy` в MS SQL Server интервала нет: разница требует двух полных проходов по кэшу планов (для последних часов есть `--hours`); в PostgreSQL — есть. Пауза прерывается Ctrl+C.

В консоль — первые `--top` строк (по умолчанию 20) и основные колонки, одна строка таблицы на строку консоли, длинные значения обрезаны. `--csv` пишет все строки и все колонки (с планом, смещениями оператора, исходным запросом) в файл CSV того же вида, что файлы таблиц: разделитель `;`, UTF-8 с BOM, переводы строк внутри значения — `\n`. Без имени файла — `<вид>_<время сервера>.csv` в текущей папке (или в `OUTPUT_DIR`).

`--kill N` закрывает сессию N (ее открытая транзакция откатывается), `--cancel N` отменяет только текущий запрос сессии (только PostgreSQL; в MS SQL Server чужой запрос можно только закрыть вместе с сессией). Что показывают команды для PostgreSQL — в разделе «PostgreSQL». Обе команды показывают, чья это сессия, и выполняются только после ответа `y` в окне консоли: без консоли (ввод перенаправлен) — ошибка. Системные сессии (номер до 50) и подключение самого скрипта закрыть нельзя.

Подключения команд — с `APP=CompareQuery show`; в своих же списках они не показываются.

## Коды возврата

| Код | Значение |
|---|---|
| 0 | успех; в режиме 2 результаты идентичны |
| 1 | режим 2: найдены различия |
| 2 | ошибка (в том числе прерванный запуск) |

## Запуск из другой программы

Для графической оболочки (наброски — `GUI.md`), которая запускает скрипт фоновым процессом без окна консоли:

- строка `stop` в stdin действует как Ctrl+C (в режиме 3 — как нажатие клавиши). stdin читается, только если это не консоль; на Windows — только канал (pipe), а файл или `NUL` команд не дают;
- `--parent-pid PID`: то же самое, если закрылась программа с процессом PID (например, GUI упал). Процесс открывается один раз при старте скрипта, поэтому новый процесс с тем же номером не спутается. Если процесса PID нет уже при старте — ошибка, код 2.

В отчете причина остановки: `ЗАПУСК ПРЕРВАН: остановлено командой stop` или `ЗАПУСК ПРЕРВАН: закрылась программа, запустившая скрипт (PID N)`. В отличие от Ctrl+C, такая остановка не ждет конца долгого оператора: текущий оператор отменяется на сервере (`SQLCancel`, как кнопка отмены в SSMS), и запуск прерывается сразу. Начатая обработка уже полученных таблиц и запись отчета доделываются.

После любого прерванного запуска без `--rollback` скрипт выполняет `IF @@TRANCOUNT > 0 ROLLBACK`: сервер не откатывает транзакцию, открытую самим скриптом (`BEGIN TRAN`), когда оператор прерван ошибкой или отменой, и ее блокировки иначе держались бы до отключения. Операторы, завершенные до прерывания без транзакции, остаются выполненными (autocommit).

```
python CompareQuery.py query.sql --repeat 3 --parent-pid 1234 --events
```

### Ход выполнения (`--events`)

С `--events` скрипт пишет в stdout по строке JSON на каждое событие, а текст отчета в stdout не выводит (он в файле). Сообщения для человека по-прежнему идут в stderr. Новых запросов к серверу события не добавляют: в них только то, что скрипт и так узнает. У каждого события есть поля `event` и `time` (часы компьютера с миллисекундами — по ним удобно считать длительности). Время сервера на тот же момент дает событие `clock`: разница `server_time - time` переводит любое `time` во время сервера. Сообщения SQL с `--events` не выводятся в stderr: они приходят событиями `message`.

| Событие | Когда | Поля |
|---|---|---|
| `start` | начало | `mode` (`run`, `session`, `compare`); для `run`: `sql`, `repeat`, `profile`, `rollback`, `batches`; для `session`: `session`, `folder`; для `compare`: `a`, `b` |
| `pass` | начало прогона | `k`, `of` |
| `clock` | часы сервера измерены (первое подключение) | `server_time` |
| `message` | сообщение SQL (`PRINT`, `RAISERROR`, ошибка; служебные не приходят) | `pass`, `server_time`, `text` (без префикса драйвера), `error` |
| `slow` | `--profile`, `--session`: ответ на запрос выборки дольше 80 мс | `count`, `ms` (сколько задержек и их сумма с начала прогона или наблюдения); в режиме 1 и `pass` |
| `batch` | начало батча | `pass`, `k`, `of`, `ignored` (служебный батч), `line` (первая строка в SQL-файле), `text` (начало текста одной строкой) |
| `table` | таблица получена | `pass`, `n`, `rows` |
| `counters` | затраты прогона с его начала: в начале батча, после каждой таблицы, в конце батча; с `--profile` еще раз в секунду по выборке | `pass`, `time_ms`, `cpu_ms`, `logical_reads`, `physical_reads`, `client_ms` (`null`, если ожидания клиента нет) |
| `statement` | `--profile` и `--session`: начался другой оператор | `object`, `line`, `text` (начало текста одной строкой), `wait`, `blocked_by`; в режиме 1 и `pass` |
| `wait` | у того же оператора сменилось ожидание | `wait` (`null` — ожидания нет), `blocked_by`; в режиме 1 и `pass` |
| `idle` | запроса нет | в режиме 1 `pass` |
| `aborted` | прогон прерван | `pass`, `reason` |
| `flush` | `--session`: файлы реестра перезаписаны | `folder` |
| `stopped` | `--session`: наблюдение завершено | `reason` |
| `report` | записан отчет или файл сравнения | `path` |
| `done` | последнее событие | `code` (код возврата), `error` (текст ошибки или `null`) |

`blocked_by` — номер сессии, которую ждет запрос (`blocking_session_id`), если он положительный и не своя сессия (у параллельного плана там своя). Счетчики с `--profile` между замерами считаются как у контрольного подключения: счетчики сессии перед батчем плюс счетчики запроса из выборки; ожидание клиента в них — на момент последнего замера.

```
{"event": "statement", "time": "2026-11-11T09:13:41.207", "object": "dbo.CalcSalary", "line": 154, "text": "update s set Amount = r.Rate * s.Hours from #sal s ...", "wait": "LCK_M_U", "blocked_by": 112, "pass": 2}
```

## Графический интерфейс

`CompareQueryGUI.py` — окно поверх тех же файлов и того же скрипта: скрипты рабочей папки, запуски, сравнение с опорным, наблюдение за сессиями. Принципы и экраны — `GUI.md`.

```
pip install pywebview
python src\CompareQueryGUI.py
```

Или `CompareQueryGUI.exe` в корне (программа — в подпапке `src`, текущая папка — корень, рядом с exe): находит Python 3.10+, при необходимости в окне консоли ставит недостающие пакеты (pywebview, pyodbc) с логом установки и запускает интерфейс без консоли. Нет Python — сообщение об ошибке.

- Нужен WebView2 (есть в Windows 10/11; на Windows 8.1 ставится отдельно, последняя версия для нее — 109). Файлы интерфейса — в папке `src\gui`.
- Время суток в окне — по часам сервера, как в файлах. Бегущее время (сколько идет запуск, оператор, ожидание) считается по часам компьютера.
- В журнале запуска вместе с ходом выполнения видны сообщения SQL (метка `SQL`, ошибки — красным); тот же журнал — на итоге запуска (из `<запуск>_message.txt`). Плашка «Задержки выборки» (`--profile`, наблюдение) краснеет, если задержки в сумме больше 5 с или больше 1% времени запроса (и не краснеет, если они меньше 0,05% времени запроса): распределение времени по операторам тогда менее точное.
- Широкие таблицы прокручиваются вбок полосой, которая прилипает к низу окна, пока таблица на экране (и Shift+колесом). Содержимое CSV открывается сразу и для больших файлов: читаются по 500 строк, дальше — «показать еще»; любая длинная таблица тоже показывает первые 500 строк и «показать еще 500». Колонки перетаскиваются за заголовок и скрываются (значок «Колонки»), клик по заголовку сортирует; порядок и видимость запоминаются для вида таблицы и одинаковы у всех запусков (реестр, журнал, CSV таблицы N скрипта, текущие и тяжелые запросы, список сессий, операторы сравнения). Любую таблицу можно свернуть значком справа в ее заголовке; свернутость тоже запоминается для вида таблицы. В реестре рядом с оператором — число его запусков `×N`.
- Редактор SQL подсвечивает синтаксис (ключевые слова, строки, комментарии, переменные, временные таблицы, числа). Переключатель «Предложить игнорируемые колонки» в параметрах запуска: два прогона (первый — прогрев), после запуска — окно игнорируемых колонок с колонками, которые различаются между прогонами; параметры такого запуска не запоминаются.
- У строк таблиц действия — значками в начале строки (текст оператора, план, наблюдать сессию и т. п.), то же — в меню по правой кнопке. Журнал длиннее 100 строк свернут по умолчанию. Окно по умолчанию — 1728×972, на экране меньше — 90% экрана.
- Игнорируемые колонки правятся в окне (значок фильтра у скрипта в панели и в редакторе, «Игнорировать …» на экране сравнения): итоговый список для скрипта с источником каждой колонки, добавление с областью «только этот скрипт» / «все скрипты группы» / «все скрипты», автоопределение двойным прогоном. Окно пишет `ignored_columns` в `CompareQuery.json` в том же виде, что читает CLI.
- Экран сравнения: вердикты по данным и по времени, различающиеся таблицы с примерами строк, идентичные списком, значимые изменения операторов таблицей (с ожиданием и началом текста из реестра). Полный текст отчета режима 2 — свернутой карточкой внизу.
- На экране сравнения у различающейся таблицы кнопка «Сравнить отличия»: два CSV только с отличающимися строками (рядом с CSV таблицы запуска B, имена `<таблица B>__<запуск A>_diff_A.csv` и `_diff_B.csv`) открываются в программе сравнения, под ней — папка с этими файлами.
- Внешний diff (кнопки «Сравнить с опорным», «Сравнение в diff», «Сравнить скрипты», «Сравнить CSV», «Сравнить отличия»): программа из настроек (клик по базе вверху панели), иначе из `git config diff.tool`, иначе TortoiseGitMerge, TortoiseMerge, WinMerge, `code --diff`. В подсказке кнопки — какие файлы и какой программой откроются.
- На итоге запуска — график времени по линейке: запуски, связанные файлами сравнения (сравнимые); клик по точке открывает запуск.
- Заметки — к запускам и к наблюдениям (под заголовком итога, видны в дереве).
- У идущего запуска под временем прогона — грубая оценка по последнему похожему запуску (тот же скрипт, столько же прогонов, тот же профиль): «≈ 63% · осталось ≈ 01:20».
- В примерах отличий строк длинные значения (больше 20 символов) показаны двумя строками — старое над новым, буква под буквой.
- Уведомление Windows, когда запуск или наблюдение закончилось, если шло дольше 30 с, а окно не активно (выключается в настройках: клик по базе вверху панели). Клик по уведомлению итог не открывает.
- Настройки (клик по базе вверху панели): список сохраненных подключений «сервер — база — логин» и «+ новое соединение»; выбор заполняет поля ниже, значки — добавить как новое и убрать из списка, «Проверить» — вход и легкий запрос с введенными значениями (сервер, база, логин, версия). «Сохранить» делает выбранное подключение активным — его использует `CompareQuery.py` (верхние ключи `connection_string`, `login`, `password`), список хранится в разделе `"GUI"`. Активное подключение из списка не убирается.
- Пока не задано ни одного подключения (активное — из примера: `localhost`, `master`, `sa`, и в списке нет других), у кнопки подключения вверху панели всплывает подсказка «Для начала задайте подключения к базе» — при запуске и при нажатии «Новый скрипт», «Наблюдать сессию», «Текущие запросы», «Тяжелые запросы»; тот же текст — в центре окна.
- На экране «Новое наблюдение» в таблице активных сессий фильтр «База данных» по умолчанию — база подключения; фильтры, которые не помещаются, переносятся на следующую строку.
- Язык интерфейса — русский или английский (кнопка в строке «Справка», выбор запоминается). Отчеты, CSV и вывод `CompareQuery.py` остаются на русском: это данные, которые разбирают сравнение и GUI.
- В наблюдении реестр операторов стоит над журналом; кольцо у его заголовка заполняется за 10 с до следующего обновления файлов и обнуляется, когда они пришли.
- В итоге запуска у таблицы, различающейся с опорным, кнопка «Отличия» раскрывает итог сравнения таблицы и примеры строк: какие изменены (было → стало), каких нет в опорном или в этом запуске. Сравнение то же, что в режиме 2, по двум CSV, без сервера и без записи файлов.
- Запуски, наблюдения и сравнения GUI выполняет процессами `CompareQuery.py` с `--events --parent-pid`, поэтому результаты те же, что из консоли, а при закрытии окна процессы останавливаются (текущий оператор на сервере отменяется).
- Сам GUI обращается к серверу только легкими чтениями системных представлений (DMV), одним своим подключением (`APP=CompareQuery gui`):
  - список сессий на экране «Новое наблюдение» — при открытии и по кнопке;
  - **«Текущие запросы»** (меню): раз в 4 с, пока окно видно (свернутое не опрашивает сервер), — пользовательские сессии с запросом и те, кто блокирует других (у простаивающих — их последний запрос); прогоны CompareQuery видны, скрыты только его служебные подключения, итоги по серверу плашками (сессий, выполняется, ждут блокировку, ждут память, очередь на процессор, самый долгий запрос). Колонка «Исходный запрос» — первоначальный вызов клиента (например, `exec` процедуры с параметрами), с сервера берется один раз на новый запрос (SQL Server 2014 SP2+). Кольцо — отсчет до обновления, клик по нему — пауза. У строки: текст запроса, план, исходный запрос (что прислал клиент: вызов процедуры с параметрами), наблюдать сессию, временные данные сессии (экран «База данных», раздел «Временные данные» с подсвеченной сессией), отменить запрос (только PostgreSQL), KILL;
  - **«Нагрузка сервера»** (меню) — что нагружает сервер. Сверху — база (по умолчанию база подключения, или «Все») и период: накоплено с перезапуска сервера (или сброса статистики) либо замер за 10, 30, 60 с — два снимка статистики с паузой, все открытые разделы за одни и те же секунды. Разделы раскрываются кликом, открыт один раздел (при открытии другого прежний сворачивается), при первом заходе все свернуты; запрос к серверу — при открытии раздела и по кнопке «Обновить», свернутые разделы сервер не спрашивают. Кнопки в строках таблиц подписаны тем, куда ведут («К таблице «Ввод-вывод»», «К экрану «Текущие запросы»…»). Желтый треугольник с «!» рядом с объектом или числом — подсказка (при наведении), на что обратить внимание: например, индекс не читается, но обновляется при каждом изменении таблицы, или у индекса тот же ключ, что у другого:
    - **«Тяжелые запросы»** — операторы из статистики кэша планов (`sys.dm_exec_query_stats`; у PostgreSQL — `pg_stat_statements`), отсортированные по выбранному показателю (CPU, время, чтения — всего или на выполнение, наибольшее время, записи, выполнения). У MS SQL Server — свой отбор «Выполнялись: за последний час, сутки, неделю» (замера за секунды нет: он требовал бы двух полных проходов по кэшу планов); отбор по базе — среди самых тяжелых запросов всего сервера;
    - **«Ожидания»** — полоса долей (блокировки, диск, CPU, клиент, память, параллелизм, страницы, прочее; при наведении на группу — что это и какие ожидания в нее вошли) и таблица. MS SQL Server — ожидания всего сервера без фоновых (`sys.dm_os_wait_stats`), без деления по базам. PostgreSQL — выборка активных сессий раз в 100 мс (накопленных ожиданий у него нет, поэтому всегда замер, по умолчанию 10 с): сессий, самый частый запрос, отбор по базе есть. У блокировок — переход к «Текущим запросам» (сначала блокирующие), у диска — к «Вводу-выводу» и к запросам с наибольшим числом чтений;
    - **«Ввод-вывод»** — MS SQL Server: файлы баз (`sys.dm_io_virtual_file_stats`), главное — среднее ожидание на операцию: чтение данных дольше 20 мс, запись лога дольше 5 мс — красным (медленный диск); переход к «Месту» этой базы. PostgreSQL: `pg_stat_io` (с 16) — доля чтений из кэша (ниже 90% — красным), запись обычных страниц самим процессом клиента (обычно это делают фоновые процессы); деления по базам нет;
  - **«База данных»** (меню) — выбранная база (по умолчанию база подключения). Только каталог и статистика сервера, данные таблиц не читаются:
    - **«Место»** — MS SQL Server: файлы базы — размер, занято, свободно в файле, прирост, предел, свободно на диске и «можно занять еще» (с учетом свободного в файле, прироста, предела и диска; меньше 1 ГБ или 10% — красным, прирост в процентах — красным); сверху итог по данным и логу. Диски — при праве `VIEW SERVER STATE`. PostgreSQL: размеры баз, свои табличные пространства, папка WAL и слоты репликации (неактивный слот держит WAL, пока его не прочитают); свободное место на диске средствами SQL не узнать;
    - **«Таблицы»** — размеры (MS SQL Server — занято и использовано, данные, индексы, секции, куча; PostgreSQL — оценка по `pg_class`, включая TOAST, мертвые строки, последний vacuum и analyze) и обращения с перезапуска сервера (или сброса статистики). Фильтр по имени, размеру и «Не использовались». Красным: много мертвых строк (больше 20% и больше 10 тыс.), seq scan или scan по таблице больше 100 МБ чаще, чем поиск по индексу. «Байт на строку» — сколько места занимает одна строка вместе с индексами (оценка роста таблицы, от 1000 строк). У строки три подтаблицы (открыта одна): индексы — ключ, INCLUDE, условие, порядок строк таблицы (кластерный индекс; у PostgreSQL — корреляция по статистике), размер, чтения, изменения; столбцы — тип, NULL, байт (MS SQL Server — по объявленному типу; PostgreSQL — средний размер, доля NULL и число различных значений по статистике ANALYZE); триггеры — включен или отключен, когда срабатывает, события, статистика выполнения (MS SQL Server — из кэша планов: выполнений, CPU, время, чтения; PostgreSQL — вызовы и время функции триггера при `track_functions`) и SQL триггера по кнопке. Кнопки у строки — SQL создания таблицы (собирается по каталогу сервера: столбцы, ограничения, индексы, внешние ключи, триггеры и комментарии; у MS SQL Server — батчи через GO и расширенные свойства, в том числе MS_Description; у PostgreSQL — операторы через «;» и COMMENT ON; права и статистики не входят) и тяжелые запросы с именем таблицы;
    - **«Функции и процедуры»** — выполнений, CPU, время, чтения (MS SQL Server — объекты с планом в кэше; PostgreSQL — при `track_functions`); кнопка у строки — тяжелые запросы с этим объектом;
    - **«Временные данные»** (всего сервера) — MS SQL Server: сколько каждая сессия занимает в tempdb (пользовательские объекты `#temp`, `@table` и внутренние — сортировки, hash), сводка по tempdb и по кнопке — самые большие временные таблицы. PostgreSQL: временные файлы сессий (`pg_ls_tmpdir`, нужна роль `pg_monitor`) и временные файлы баз с последнего сброса статистики. У сессии — текст запроса, «Текущие запросы» и наблюдение;
  - заполненный фильтр (текст или список) — с зеленой рамкой, у текстового — крестик очистки;
  - тексты и планы — по кнопке (план открывается файлом `.sqlplan` из временной папки, обычно в SSMS).
- Единственные изменения на сервере из GUI — `KILL` сессии и, у PostgreSQL, отмена ее запроса на экране «Текущие запросы», с подтверждением (после «да» 10 с без вопросов, каждое нажатие продлевает). Для `KILL` в MS SQL Server нужно право `ALTER ANY CONNECTION`.
- Свое состояние (рабочая папка, опорный запуск, параметры запуска, свернутые группы, заметки) GUI хранит в разделе `"GUI"` файла `CompareQuery.json`; остальные ключи не трогает.
- Удаление запуска — в корзину Windows (отчет, CSV, папка реестра, файлы сравнения); наблюдения — его папка в `Sessions_profile`.
- `python src\CompareQueryGUI.py --dev` — тот же интерфейс в браузере по адресу http://127.0.0.1:8766 (для отладки, без окна).

## Формат файла данных

Одна строка базы — ровно одна строка файла. Так файлы двух запусков можно сравнить любой утилитой diff.

- UTF-8 с BOM, перевод строки `\n`, разделитель `;`.
- Первая строка: имена колонок. Далее строки данных, отсортированные по ключу.
- NULL — пустая ячейка, пустая строка — `""`. Значение с `;` или `"` либо с пробелом в начале или конце берется в кавычки, `"` внутри удваивается.
- Невидимые символы показаны явно: `\n`, `\r`, `\t`, `\\`, остальные как `\xNN`, `\uNNNN`. Это касается и неразрывного пробела, и символов нулевой ширины.
- Числа записываются без экспоненты и хвостовых нулей, поэтому `int`, `bigint`, `decimal` и `bit` с одинаковым значением записываются одинаково. Даты в ISO: `2026-01-31 10:00:00.5`. `datetimeoffset` приводится к UTC с суффиксом `Z`. Двоичные данные пишутся как `0x...`.
- Значение длиннее 200 символов обрезается: `<первые 200 символов>... len <длина> <crc32>`. Различия дальше 200 символов видны только по длине и хэшу. Значения xml, sql_variant и UDT всегда записываются в таком виде.

Это не совсем CSV: Excel откроет файл, но переносы строк в нем экранированы.

## Ключ

Ключ нужен, чтобы сортировать строки и сопоставлять их между запусками. Скрипт выстраивает колонки в порядке приоритета и берет самый короткий префикс этого порядка, уникальный по данным. Приоритет:

1. Колонка `id`.
2. Колонки, оканчивающиеся на `id` (`userId`, `order_id`).
3. Колонки, содержащие `period`, затем `num`, `name`, `fromDate`.
4. Остальные колонки в порядке таблицы.
5. Игнорируемые колонки из `ignored_columns`, в том же порядке.

В шагах 2 и 3 сначала берутся совпадения на границе слова (`userId`, `period_start`), затем любые (`PAID`, `username`). Если даже все колонки вместе не уникальны (полные дубли строк), к ключу добавляется виртуальный номер дубля `#dup`.

Затем из найденного префикса убираются лишние колонки. Последняя колонка префикса обязательна: без нее префикс не уникален. Она откладывается в ключ, и поиск самого короткого уникального префикса повторяется среди колонок перед ней, вместе с уже отложенными. Так до тех пор, пока отложенные колонки сами не станут уникальны. Пример: префикс `(id, accId, proId, hhId, acsId)`, а уникально одно `acsId` — ключом будет `(acsId)`. Если ключ `(accId, proId, acsId)`, это найдется за три повтора.

- Из такого ключа нельзя убрать ни одну колонку. Самым коротким из возможных он может и не быть, но при одних данных результат всегда один и тот же, и колонки с большим приоритетом в нем предпочтительнее.
- Колонки ключа идут в порядке приоритета, за ними остальные колонки в прежнем порядке.
- Если ключ дошел до игнорируемых колонок, лишние колонки не убираются: в нем и так все неигнорируемые.
- Каждый повтор — проверка отложенных колонок и двоичный поиск по колонкам перед последней. Для ключа из одной колонки это одна лишняя проверка. Время видно в отчете в строке «ключ» раздела «Производительность».

Порядок строк текстовый: `10` идет раньше `9`. Для сравнения этого достаточно: при совместимых ключах оба файла отсортированы одинаково, при разных они пересортировываются в памяти.

## Ограничения

- **Время зависит от нагрузки сервера.** В него входят блокировки другими сессиями, очередь к процессору и чтение с диска, а они зависят от остальных запросов. Если время изменилось при тех же CPU и чтениях, причина в ожиданиях: в реестре (`--profile`) видно, в каких. Передача результатов и работа скрипта во время не входят (см. «Контрольное подключение»).
- **Границы между таблицами приблизительны.** Сервер не ждет, пока клиент дочитает таблицу: следующие операторы могут начаться раньше, чем контрольное подключение снимет замер. Поэтому часть затрат следующего оператора иногда попадает в предыдущую таблицу. Сумма по запуску от этого не меняется.
- **Типы в `create table` приблизительны.** Драйвер не отличает `varchar` от `nvarchar` и `int` от `bigint`. Сравнение от типов не зависит.
- **`real`** приходит с хвостом (`0.10000000149...`) и не совпадет с `float` или `decimal` того же значения.
- **`datetime2(7)` и `time(7)`** читаются с точностью до микросекунды, последний знак теряется.
- **Нестабильные запросы** (`getdate()`, `newid()`, `top` без `order by`) дают различия при каждом запуске. Используйте `ignored_columns`, найти такие таблицы помогает `--repeat`, а `--repeat 2` сразу предлагает элемент настроек.
- **`GO` ищется построчно.** Строка `GO` внутри многострочного комментария `/* */` или строкового литерала тоже разделит батч.
- **Память и диск.** В памяти держится одна таблица на этапе сортировки: порядка гигабайта на миллион строк по 20 колонок. Пока таблица обрабатывается, ее данные лежат во временном файле.
