# CompareQuery — документация для разработки

Этот файл для продолжения работы с чистого контекста: как устроен скрипт, почему он устроен именно так и какие варианты отброшены после исследования. Пользовательская инструкция — [README.md](README.md). Если файлы расходятся, верно поведение кода, а README нужно поправить.

## 1. Правила работы (обязательно)

- **Не делать git commit/push.** Пользователь коммитит сам. Репозитория в папке может и не быть.
- **Не трогать** `CompareQuery_v1.py` … `CompareQuery_vN.py` (это резервные копии пользователя) и `t1.md`.
- **Дизайн:** простой и предсказуемый, без переусложнения и хаков. Тесты в проект не добавлять, пока не попросят (см. §14).
- **Отвечать по-русски.** Комментарии и сообщения скрипта тоже по-русски. В `CompareQuery.py` и README нет буквы «ё» (пишется «е»), держать единообразие.
- **Секреты:** строка подключения и пароль никогда не попадают в консоль, отчет и логи. Email пользователя приватен.
- **Термины:** ожидание (wait) — любое ожидание запроса (диск, память, CPU, сеть, блокировки); блокировка (lock) — только `LCK_M_*`. Ожидание диска или памяти «блокировкой» не называть нигде (требование пользователя). Отсюда колонки «Ожидание блокировок мс», «Ожидание ресурсов мс», «Ожидание ресурсов N место».
- **Совместимость со старыми файлами не нужна** (пользователь: «никаких данных нет»): GUI читает только текущие форматы. Старый код совместимости в CLI (§11) просто не трогали.
- **Боевой сервер чужой.** Требование пользователя дословно: «Боже упаси писать что-то на сервер, если есть выбор, то только в памяти… сервер не мой, и я не имею права там что-либо делать, ни с файлами на сервере, ни с его настройками… запросы, если они никому не помешают (строгое требование) могу запускать любые (конечно не портящие данные). Сервер боевой и одновременно выполняются десятки запросов.» Отсюда:
  - на сервере ничего не создается: ни объектов (event session, trace, таблиц), ни файлов, ни настроек;
  - кэш не очищается (`DBCC FREEPROCCACHE` / `DROPCLEANBUFFERS` запрещены);
  - из служебного разрешены только дешевые точечные чтения DMV по одной сессии (исключение, согласованное с пользователем: в GUI список активных сессий для выбора наблюдения — один легкий запрос по кнопке, `GUI.md` §5.9);
  - любой новый механизм проверять по источникам на предмет нагрузки и известных сбоев (см. §12).
- Право `VIEW SERVER STATE` у пользователя есть, версия сервера — SQL Server 2019 (15), возможно чуть ниже.

## 2. Состав и запуск

**Раскладка (пользователь перенес программу):** код — в `src/` (`CompareQuery.py`, `CompareQueryGUI.py`, `gui/`, `launcher/`, `GUI.md`), в корне — `README.md`, `README.en.md`, `CLAUDE.md`, `CompareQueryGUI.exe`, `Dev/` (черновики пользователя, `t.sql`). Лаунчер запускает `src\CompareQueryGUI.py` (или, как раньше, `CompareQueryGUI.py` рядом с собой), текущая папка — корень; `open_help` ищет README в папке скрипта, затем уровнем выше. Ниже пути без `src/` — относительно `src`.

Один файл `CompareQuery.py` (Python 3.10+, pyodbc), настройки `CompareQuery.json` рядом со скриптом, то есть в `src` (создается с примером при первом запуске). Графическая оболочка — `CompareQueryGUI.py` и папка `gui/` (pywebview, §17), лаунчер `CompareQueryGUI.exe` (исходник и сборка — `launcher/`); CLI от нее не зависит.

| Режим | Команда | Суть |
|---|---|---|
| 1 | `CompareQuery.py q.sql [--rollback] [--repeat N] [--profile]` | выполнить SQL, сохранить таблицы в CSV, написать отчет |
| 2 | `CompareQuery.py A.txt B.txt` | сравнить два отчета режима 1 (сервер не нужен) |
| 3 | `CompareQuery.py --session N` | наблюдать чужую сессию, вести реестр операторов в реальном времени |

Коды возврата: 0 — успех/идентичны, 1 — найдены различия (режим 2), 2 — ошибка или прерванный запуск.

Порядок секций в файле: константы → служебные функции → настройки и строка подключения → чтение SQL и батчи → конвертеры типов и обработка «200» → канонический текст → ключ → `create table` → обработка таблицы в исполнителе → режим 1 (Control, Sampler, StatsBuilder, Pass, реестр, Mode1Run) → режим 3 (SessionMonitor) → режим 2 (разбор отчета, Merger, сравнение реестров) → `main`.

## 3. Режим 1: конвейер

### 3.1. Подготовка
- `read_settings`: ключи JSON без учета регистра. `build_conn_str` дописывает `UID=…;PWD={…}` (значение в `{}` с удвоением `}`), если `login` задан. Если в строке нет `APP`, добавляется `APP=CompareQuery` (рабочее), `CompareQuery control` (контрольное), `CompareQuery session` (режим 3). По `APP` администратор видит чужие сессии.
- `read_sql`: BOM → UTF-8 → cp1251. `split_batches`: строка из одного `GO` (с пробелами и комментарием) делит батчи, `GO N` не поддерживается. Каждый батч хранится как `(первая строка в файле, текст)`: по первой строке потом считаются номера строк операторов SQL-файла в реестре.
- `ignored_columns`: список групп `{"mask": "...", "tables": {"*": [...], "2": [...]}}`. Маска — fnmatch по имени SQL-файла без расширения, без учета регистра. Колонки всех подходящих групп объединяются. На старый формат `"columns"` — понятная ошибка с примером.

### 3.2. Прогон (`Pass`) — для каждого из N прогонов заново
1. Рабочее подключение (`autocommit=not rollback`), `pyodbc.native_uuid = True`, конвертеры вывода для типов, которые pyodbc не понимает: -155 datetimeoffset, -152 xml, -151 UDT, -150 sql_variant.
2. `SELECT @@SPID`, затем контрольное подключение (`autocommit=True`) → `Control`. Если оно не открылось или не видит сессию, запуск идет дальше без счетчиков («Счетчики сервера: нет данных (причина)»).
3. С `--profile` стартует поток `Sampler` на том же контрольном подключении (доступ под `threading.Lock`).
4. `run_batches`: для каждого батча `control.batch_start()` → `execute` → цикл: если есть `description`, `receive_table`, иначе запоминается `rowcount`; `nextset`. После батча `control.now()` дает итог прогона.
5. В `finally`: остановка сэмплера, `rollback` (если `--rollback`), закрытие рабочего подключения. В последнем прогоне с `--profile` планы забираются **после** закрытия рабочего, но до закрытия контрольного.

Новые подключения на каждый прогон нужны, чтобы `#temp`-таблицы и `SET`-настройки не переходили между прогонами. С `--rollback` откат делается после каждого прогона, чтобы транзакция жила меньше.

### 3.3. Двухэтапная обработка таблицы
**Этап 1, главный процесс (`receive_table`)** — максимально легкий, чтобы не задерживать сервер (пока клиент не забрал строки, сервер стоит в `ASYNC_NETWORK_IO`):
- `fetchmany(FETCH_BLOCK)` блоками, блок транспонируется в колонки;
- вид колонки (`kind_of`) определяется по первому не-NULL значению;
- обработка «200» (`stage1_check`): значение длиннее `MAX_CELL_LEN` заменяется маркером `<200 символов>... len N crc32`. Для `str`/`bytes` с объявленным размером ≤ 200 проверка пропускается целиком (экономия на коротких колонках); xml, sql_variant, UDT и неизвестные виды всегда превращаются в маркер;
- блоки колонок пишутся `pickle` во временный файл (память главного процесса не растет);
- после последнего блока `control.now()` дает «затраты до таблицы», задача уходит исполнителю.

**Этап 2, исполнитель (`process_table`)** — `ProcessPoolExecutor(max_workers=1)` (`WORKER_MODE="process"`). Отдельный процесс, чтобы обработка предыдущей таблицы не отнимала GIL у приема следующей и не искажала замеры. Исполнитель игнорирует SIGINT: Ctrl+C обрабатывает главный процесс, начатая таблица дорабатывается. Шаги:
1. Канонический текст каждой ячейки (§4), для строковых видов — `casefold` (для чисел, дат и т. п. свертка пропускается, `NO_FOLD`).
2. Хэш колонки = сумма `crc32` свернутых значений по модулю 2^64. **Сумма не зависит от порядка строк**: хэши сравнимы без сортировки и между прогонами с разным порядком.
3. Хэш таблицы = сумма `crc32` строк (свернутые значения через `\x00`) **без игнорируемых колонок**: строки, отличающиеся только в них, считаются одинаковыми.
4. Промежуточный прогон `--repeat` (`out is None`) на этом заканчивается: нужны только хэши.
5. Ключ (§5), сортировка индексов строк по свернутым значениям ключа, запись файла данных блоками по `WRITE_CHUNK`.

В памяти одновременно одна таблица (около 1 ГБ на миллион строк по 20 колонок).

### 3.4. Повторы `--repeat N` (N ≥ 2)
- Первый прогон — прогрев: кэш не чистим (запрещено), поэтому вместо «холодного» старта прогрев. Счетчики и реестр — медиана прогонов 2..N (`median_vec`).
- Данные (CSV) пишутся только в последнем прогоне.
- «Недетерминированные таблицы»: у таблицы различается `(rows, table_hash)` между прогонами.
- При N = 2 в конце отчета `# Предложение для настроек` (`ignore_suggestion`): колонки, у которых различается **хэш колонки** между прогонами, независимо от текущих настроек. Маска — имя файла, `[` экранируется как `[[]` (`*` и `?` в именах файлов Windows невозможны). Таблицы с разным числом строк в элемент не входят.

### 3.5. Служебные батчи `--ignore in test`
Первая непустая строка батча — `-- ignore in test` (`IGNORE_RE`, без учета регистра). `run_ignored`:
- батч выполняется, таблицы вычитываются и отбрасываются, нумерация таблиц их не учитывает (поэтому запуск сравним с запуском без служебных батчей);
- затраты исключаются **сдвигом базы**: дельта батча `end - start` прибавляется к `first` и `mark`. Так ни сводка, ни «затраты до таблицы» не меняются, и не нужен отдельный учет;
- сэмплер получает `ignoring=True` и запоминает `(request_id, start_time)` такого запроса в `ignored_requests`, чтобы отбросить и запоздавшие выборки;
- в «Производительности» одна строка `Батч N: --ignore in test, в отчет не попадает`. Ограничений на позицию батча нет.

### 3.6. Ошибки и прерывание
Ошибка сервера или Ctrl+C: уже полученные таблицы дорабатываются, в отчет `ЗАПУСК ПРЕРВАН: …`, код 2. Не полностью полученная таблица не сохраняется (`partial`). Ctrl+C срабатывает только когда драйвер вернул управление. Повторный Ctrl+C во время ожидания исполнителя — выход без отчета (`shutdown(cancel_futures=True)`).

**Остановка из другой программы (`Stop`, для GUI).** У фонового процесса без консоли нет клавиатуры, а Ctrl+C до него в Windows доходит ненадежно. Два источника, оба только запоминают причину (`Stop.request`, действует первая):
- строка `stop` в stdin — поток читает `os.read(0)`, только если stdin не консоль (иначе он отнимал бы нажатия у `msvcrt`). Не `sys.stdin`: поток, ждущий в буферизованном stdin, может сорвать завершение интерпретатора. **На Windows поток не ждет в чтении** (`stdin_waiter`): пока идет синхронный `ReadFile` канала, другие операции с ним ждут, и процесс-исполнитель при старте зависал на проверке stdin (проверено: запуск висел на первой таблице, пока GUI держит stdin открытым). Поэтому раз в 0,2 с `PeekNamedPipe`, читается только пришедшее; stdin не канал (файл, `NUL`) — команд нет. В тестах закрывать stdin нельзя (`communicate()` закрывает его сразу и прячет зависание);
- `--parent-pid PID` — процесс открывается один раз при старте (`OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject`, без опроса; вне Windows — `os.kill(pid, 0)` раз в секунду), поэтому новый процесс с тем же номером не спутается. Нет процесса при старте — ошибка.

**Отмена оператора.** На время `run_batches` рабочий курсор регистрируется (`Stop.set_cancel(cur.cancel)`), и `Stop.request` вызывает `cursor.cancel()` из своего потока: pyodbc вызывает `SQLCancel` без GIL, метод задуман для вызова из другого потока; сервер получает attention и прекращает оператор, драйвер возвращает в главный поток ошибку `HY008 Operation canceled`, причиной прерывания пишется `Stop.reason`. Вызов и снятие регистрации — под `Stop.lock`, поэтому курсор не закроется посреди `SQLCancel`. Ctrl+C так не умеет: обработчик сигнала Python работает в главном потоке только после возврата из драйвера. По источникам: attention не откатывает открытую транзакцию (это обязанность клиента), поэтому после любого прерывания без `--rollback` — `IF @@TRANCOUNT > 0 ROLLBACK` (снимает блокировки транзакции, открытой самим скриптом; с `--rollback` и так `conn.rollback()`). Источники: [pyodbc cursor.cpp, Cursor_cancel](https://github.com/mkleehammer/pyodbc/blob/master/src/cursor.cpp), [SQLCancel](https://learn.microsoft.com/sql/odbc/reference/syntax/sqlcancel-function), [How It Works: Attention](https://techcommunity.microsoft.com/blog/sqlserversupport/how-it-works-attention-attention-or-should-i-say-cancel-the-query-and-be-sure-to-process-your-results/315511). На реальном сервере не проверено (спецификация ODBC не гарантирует, что отмена сработает: тогда остановка, как раньше, — после возврата драйвера).

Режим 1 проверяет запрос (`Stop.check` → `StopRequested`) в тех же местах, где срабатывает Ctrl+C: перед батчем, после `execute`/`nextset` (`timed`), после каждого `fetchmany`, в `run_ignored`. Дальше как Ctrl+C: `ЗАПУСК ПРЕРВАН: <причина>`. Не через `_thread.interrupt_main()`: прерывание пришло бы в любой точке, в том числе во время ожидания исполнителя (отчет потерян) или в `finally` с откатом. Поэтому остановка во время обработки таблиц не прерывает ее, а срабатывает у следующего прогона. Режим 3 проверяет `Stop.reason` в цикле ожидания вместе с клавишей. Повторный запрос ничего не делает: GUI при закрытии шлет `stop` и сам завершается, и смерть родителя не должна стать «вторым Ctrl+C».

**События `--events` (`Events`, для GUI).** По строке JSON на событие в stdout (список и поля — README, «Ход выполнения»), отчет в stdout не дублируется (`write_report`), справка при неверных аргументах — в stderr. `main` всегда завершает событием `done` (код и текст ошибки, `dispatch` возвращает пару). Закрытый stdout выключает события молча. Принцип: **ни одного нового запроса к серверу** — события берутся из того, что скрипт уже знает:
- `counters` — в тех же точках, где и так меряет `Control` (начало батча, после таблицы, конец батча), через `Pass.emit_counters` (затраты от `first`; служебный батч в них не попадает, т. к. в `run_ignored` не вызывается, а после него `first` сдвинут). С `--profile` еще раз в секунду в потоке выборки (`Sampler.on_poll` → `Pass.on_sample`) по формуле `Control.now`: `base` + счетчики запроса из выборки, ожидание клиента — из последнего замера, `vmax` с `control.last` против отката;
- текущий оператор — `Sampler.now(s)` (общий для строки состояния `--session` и событий), изменения отслеживает `NowEvents`: `statement` при смене ключа (запрос, оператор), `wait` при смене ожидания или `blocked_by` у того же ключа, `idle` — запроса нет;
- `clock` — один раз, когда измерены часы сервера (§3.8); `time` всех событий — часы компьютера (по ним GUI считает длительности), `server_time - time` из `clock` переводит их во время сервера;
- `message` — сообщение SQL (§3.8), с `--events` вместо строки в stderr (иначе GUI показал бы его дважды);
- `slow` — из `Sampler.timed_query` при каждой задержке выборки (`count`, `ms` с начала прогона/наблюдения; `Sampler.event_fields` дает номер прогона).

### 3.8. Время сервера и сообщения SQL
- **`ServerTime`**: часы сервера по одному замеру — `query_spid` выполняет `SELECT @@SPID, SYSDATETIME()` (запрос и так нужен, лишнего нет; момент замера — середина вызова), дальше время = замер + прошедшее по `perf()`. Устанавливается один раз за процесс (первое подключение; в режиме 1 — рабочее, в режиме 3 — свое). До замера `ServerTime.at/now` дают часы компьютера. Требование пользователя: время суток везде по серверу (может быть в другом часовом поясе). По серверу: «Дата выполнения», имена отчета/CSV/папки реестра (`Mode1Run.run_id()` — вычисляется при первой записи, когда часы уже известны), папка и шапка `--session`, строка состояния, сообщения. Если часы компьютера отличаются больше чем на минуту, в отчете строка «Часы компьютера». Исключения: файлы сравнения режима 2 (сервера нет) и поле `time` событий.
- **Сообщения** (`Pass.grab` → `show_message`): все сообщения по-прежнему копятся для раздела «Производительность» (сырые, с префиксом драйвера). Показываются по ходу (`user_message`): kind у pyodbc — `"[SQLSTATE] (номер)"`; PRINT — номер 0, RAISERROR с текстом — 50000, пользовательские ≥ 50000, ошибки — SQLSTATE не классов `00`/`01`; служебные информационные (5701, 5703, 8153…) — нет. Префикс `[Microsoft][ODBC…][SQL Server]` убирается. Время — серверное в момент `grab` (драйвер вернул управление). По документации ODBC каждое информационное сообщение — отдельный результат, поэтому `RAISERROR … WITH NOWAIT` приходит через `nextset` сразу; `PRINT` сервер буферизует. На реальном сервере не проверено (README, «Что проверить»). Служебные батчи `grab` не вызывают — их сообщений нет нигде.
- **Консоль**: `report()` возвращает (файл, консоль); в консоль не идет раздел «Производительность» (пользователь: «там до мегабайта спама»), «Предложение для настроек» идет.

### 3.7. Выходные файлы
- Отчет `q_<время>.txt` рядом с SQL (или в `OUTPUT_DIR`), в консоль — без раздела «Производительность».
- **Журнал запуска** (`Journal`, только режим 1, `Journal.on` в `run_mode1`): `log()` и `show_message` складывают строки `(perf(), метка, текст)`; в конце `Mode1Run.write_journal` пишет `<run_id>_message.txt` в подпапку данных (имя выбрал пользователь), в отчете строка `Журнал: q/q_<время>_message.txt`. Время пересчитывается в серверное при записи (`ServerTime.at`): первые строки появляются раньше замера часов. Формат строки: `[чч:мм:сс.ммм] SQL: текст` / `Ошибка:` / без метки — строка CLI; продолжение многострочного — с отступом. GUI читает его `read_journal` (`run_details` → `journal`). Новых запросов к серверу нет.
- Подпапка `q/` (по имени SQL без расширения, общая для всех запусков): `q_<время>_<N>.csv`, папка реестра `q_<время>_profile/`, журнал запуска `q_<время>_message.txt`. `q_<время>` (`run_id`) — идентификатор запуска, поэтому номер таблицы после времени (требование пользователя); время — сервера (§3.8).
- Пути в отчете относительные (отчет вместе с подпапкой переносим). Старые отчеты без подпапки тоже читаются: файл ищется рядом с отчетом.
- Ничего не перезаписывается: `unique_path` добавляет `_2`, `_3`.

## 4. Канонический текст и формат данных

Цель: одно и то же значение всегда дает один и тот же текст, а одна строка БД — ровно одна строка файла (файлы двух запусков сравнимы любым diff).
- NULL внутри обработки — `NUL = "\x01"` (в каноническом тексте не встречается), в файле — пустая ячейка; пустая строка — `""`.
- Числа (`int`, `decimal`, `float`, `bit`) — десятичная запись без экспоненты и хвостовых нулей, `-0` → `0`. Поэтому `int` и `decimal` с одним значением совпадают. `float` идет через `Decimal(repr(v))`.
- Даты ISO, дробная часть секунд без хвостовых нулей; `datetimeoffset` → UTC с суффиксом `Z`; bytes → `0x…`.
- `escape`: `\n \r \t \\` и любые непечатные символы (`\xNN`, `\uNNNN`, `\UNNNNNNNN`), включая неразрывный пробел и символы нулевой ширины.
- `format_cell`: кавычки, если есть `;`, `"` или пробел на краю. `parse_line` — точное обратное.
- Сравнение без учета регистра (`casefold`), в файлах значения как есть.
- Имена колонок: пустые → `column_N`, дубли (без учета регистра) → `_2`, `_3` (`make_names`).

## 5. Подбор ключа

1. **Порядок приоритета P** (`key_order`): `id` → оканчивающиеся на `id` → содержащие `period`, `num`, `name`, `fromDate` → остальные по порядку таблицы → игнорируемые колонки в том же порядке. В шагах 2–3 сначала совпадения на границе слова (camelCase или `_`), затем любые.
2. **Кратчайший уникальный префикс** (`find_key_len`): проверка первой колонки, проверка всех (если не уникальны — полные дубли, добавляется виртуальная `#dup`), затем двоичный поиск длины. Уникальность — `len(set(zip(...))) == nrows`.
3. **Минимизация** (`minimal_key`, идея пользователя): последняя колонка префикса обязательна (без нее префикс не уникален), она откладывается в `found`. Затем двоичным поиском ищется кратчайший префикс оставшихся колонок, который вместе с `found` уникален, его последняя колонка добавляется в `found`, и так пока `found` не станет уникальным. Итог — ключ, из которого нельзя убрать ни одну колонку (не обязательно кратчайший из возможных, но детерминированный: решают приоритеты). Колонки ключа идут в порядке P, затем остальные.
   - Не минимизируется, если префикс дошел до игнорируемой колонки или есть полные дубли.
   - Цена: примерно `s · log2(k)` проверок для ключа из s колонок.
4. Сортировка строк — по свернутым текстам ключа (текстовый порядок: `10` < `9`, для сравнения этого достаточно). При полных дублях ключ — все свернутые колонки + все оригинальные (детерминированный порядок дублей).

Зачем минимизация: короткий ключ сопоставляет строки по сути. Пример пользователя: с длинным ключом `(id, accId, proId, hhId, acsId)` строка с измененным `hhId` выходила парой «только в A / только в B», с минимальным `(acsId)` — как «различие в hhId».

## 6. Контрольное подключение (`Control`)

Вектор счетчиков `CTL_ZERO = (cpu, logical_reads, reads, writes, wall_ms, client_ms)`.
- Один запрос `COUNTERS_SQL`: `sys.dm_exec_sessions s LEFT JOIN sys.dm_exec_requests r` по `session_id` + подзапрос `SUM(wait_time_ms)` по `ASYNC_NETWORK_IO` из `sys.dm_exec_session_wait_stats`. Наличие этого DMV (SQL Server 2016+) проверяется пробой `SELECT TOP 0 …`; без него `client_ok=False`, в отчетах «ожидание клиента: нет данных», и время включает ожидание клиента.
- **Счетчики сессии обновляются только в конце батча** (документация `sys.dm_exec_sessions`). Поэтому `batch_start()` берет полные счетчики сессии как базу, а `now()` внутри батча = база + счетчики текущего запроса. Если запрос уже закончился (`r` NULL), берется максимум из счетчиков сессии и база + последний запрос. `vmax` с предыдущим значением делает ряд монотонным.
- **Время** `run_time(c) = max(wall - client, 0)`: часы скрипта минус ожидание клиента. Так из времени уходят передача результатов и работа скрипта, а блокировки, диск и очередь к CPU остаются (это реальная цена запроса). Пользователь сначала выбрал CPU, затем попросил переориентироваться обратно на время, но без клиента.
- «Затраты до таблицы» = `now` после получения таблицы минус `mark` (предыдущая таблица или начало первого батча). Граница приблизительна: сервер может начать следующие операторы до замера, сумма по запуску верна.
- Без права или при сбое контрольного подключения запуск продолжается без счетчиков (`measure` возвращает None и запоминает причину).

## 7. Профилирование выборкой (`Sampler` + `StatsBuilder`)

Используется в `--profile` (поток, `run()`) и `--session` (вызов `poll()` из главного цикла).

**Выборка** раз в `PROFILE_INTERVAL_MS=100` мс — два легких запроса по одной сессии (пользователь просил: сервер бывает медлит с ответами из системных представлений, поэтому лучше несколько маленьких запросов, чем один составной): `REQUEST_SQL` — строка `sys.dm_exec_requests` по `session_id` (`request_id, start_time, sql_handle, statement_start/end_offset, plan_handle, cpu_time, logical_reads, reads, total_elapsed_time, wait_type, last_wait_type, status, granted_query_memory, SYSDATETIME(), blocking_session_id`), и `BLOCKING_SQL` — `TOP 1` по `blocking_session_id = spid` (блокирует ли кого-то; только если запрос есть). Кортеж: `(req=(request_id,start_time), handle, start, end, plan, (cpu,lr,pr,elapsed), (wait_type,last_wait,status,mem_pages,blocking,blocked_by), server_time)`. `blocked_by` — `blocking_session_id` своей строки (кого ждет запрос; пользователь согласовал как бесплатный: та же строка): только > 0 и не своя сессия (у `CXPACKET` там своя), иначе None. В реестр не идет, только в строку состояния (`LCK_M_U ждет 112`) и события.

**Задержки выборки**: только запрос строки запроса сессии (`REQUEST_SQL`, от его ответа зависит точность времени), ответ на который дольше `SAMPLE_SLOW_MS=80`, увеличивает `Sampler.slow` и `slow_ms` (полная длительность таких ответов). Выводится в шапке `registry.txt` (`sampling_lines`); в `--profile` при нескольких прогонах — сумма по измеряемым прогонам. Длительность меряет `Control.timed_query` внутри `Control.lock`: ожидание подключения, занятого замером счетчиков главного потока, не считается (раньше считалось, и плашка краснела без медленного сервера). Вспомогательные запросы не считаются: `BLOCKING_SQL` (кто ждет сессию), проверка жизни сессии в `--session`, запросы `Lookup` (свое подключение). Порог был 60 мс, поднят до 80 по просьбе пользователя.

**Тексты, объекты и планы — поток `Lookup`** со своим подключением (в `--profile` третье подключение, в `--session` второе). Раньше они запрашивались синхронно в `poll()` и задерживали выборки — пользователь заметил риск: ответ сервера на `dm_exec_sql_text`/план бывает долгим. Сейчас: `poll()` вызывает `lookup.want_text(handle)` (в очередь один раз) и кладет выборку в `Sampler.waiting`; `drain()` передает в `StatsBuilder` выборки по порядку, пока у головы очереди текст готов (`handle in texts`; текст кладется в `texts` только вместе с объектом). `None` в очереди — «запроса нет» (`builder.idle()`), тоже по порядку. Ускоренная выборка 30 мс работает с момента, когда текст функции уже получен. В конце `finish()` ждет `Lookup` не дольше `LOOKUP_WAIT_S=30` с (в `--session` — 0), остальное идет как «(текст недоступен)». Ошибка `Lookup` — в `lookup.error`, строка в шапке реестра. Кэш: `sys.dm_exec_sql_text(handle)` — один раз на handle; имя объекта — `OBJECT_SCHEMA_NAME/OBJECT_NAME(id, dbid)`; тип объекта — динамический SQL к `<db>.sys.objects` через `sp_executesql` (`OBJECTPROPERTY` работает только в текущей базе).

**Оператор** (`describe`): текст по смещениям (`offset // 2`, т. к. nvarchar — байты), строка = число `\n` до начала + 1. Если текст совпал с батчем SQL-файла, строка пересчитывается в строку файла (`batch_start`); иначе объект, или «(динамический SQL)» / «(батч)». **Идентичность оператора** — `(label, line, crc32 нормализованного текста)` (пробелы схлопнуты, casefold). Один оператор в цикле или при нескольких вызовах суммируется в одну строку.

**Распределение** (`StatsBuilder.feed`): приращение счетчиков между двумя выборками одного запроса относится к оператору второй выборки; первая выборка нового запроса — счетчики с его начала.
- **Функции** (`FN, IF, TF, FS, FT`) в реестр не попадают. Пользователь сам наблюдал «мерцание»: DMV показывает то вызывающий оператор, то оператор внутри скалярной функции. Выборка внутри функции относится к последнему оператору вне функций этого запроса (его вызвавшему), а если такого еще не было — копится в `pending` и уходит следующему. После выборки в функции следующая через `PROFILE_FAST_MS=30` мс. Pending без оператора на конец запроса уходит в `lost`.
- **Ожидания интервала** (`interval_extra`): `w = Δelapsed − Δcpu` целиком относится к одному типу (`wait_name`): текущий `wait_type`; если пусто и `runnable` — `SOS_SCHEDULER_YIELD`; иначе `last_wait_type`. `PAGEIOLATCH_/PAGELATCH_/LATCH_` сводятся в `X_*`. `ASYNC_NETWORK_IO` → клиент, `LCK_M_*` → «Ожидание блокировок», прочее → словарь ожиданий (топ-3 в реестре как `TYPE (N мс)`). Если сессию кто-то ждет, весь `Δelapsed` → «Блокировал другие сессии». Память — максимум `granted_query_memory` · 8 / 1024 МБ.
- Почему блокировки по `LCK_M_*`, а не по `blocking_session_id`: свою блокировку запрос ждать не может, а у `CXPACKET/CXCONSUMER` в `blocking_session_id` стоит своя же сессия.
- **Отрезки** (`seg`): непрерывное выполнение одного оператора. Закрывается, когда начался другой оператор или запрос закончился (`idle`), и уходит в `on_segment` (→ `log.csv`) с временем сервера начала (время предыдущей выборки или `start_time` запроса). Выборки внутри функций отрезок не прерывают.
- **Запусков** (`runs` у оператора, колонка `Запусков` реестра): +1 при начале каждого отрезка оператора — возврат к нему после другого оператора или новый запрос с ним. Предложение пользователя: считать повтор, только когда другой оператор уже ушел в журнал, — это и есть начало нового отрезка; мерцание с функциями отрезок не рвет, поэтому счетчик не накручивает (проверено сценарием A, функция, A, B, A, новый запрос → 3). Нижняя оценка: повторы между двумя выборками без другого оператора не видны. С `--repeat` — медиана прогонов. В журнале колонки нет (строка — один запуск).
- Точность — до интервала: операторы суммарно меньше ~0,5 с шумные, верхние операторы долгого запроса видны хорошо. Числа выполнений и времени процедуры с вложенными вызовами выборка не дает (видно только самый внутренний оператор).

**Планы**: `sys.dm_exec_text_query_plan(plan_handle, start, end)` — кэшированный (оценочный) план нужного оператора. В `--profile` один раз в конце (через контрольное подключение, после закрытия рабочего — выборок уже нет), только для `PROFILE_PLAN_TOP=30` верхних; в `--session` при сбросе заказываются у `Lookup` (`want_plan`, кэш по `(plan_handle, start, end)`) и попадают в файлы при одном из следующих сбросов.

## 8. Реестр: файлы и запись

- `registry.txt` — шапка (выборок, из них в функциях, распределено времени, ссылки на таблицу и журнал).
- `registry.csv` — операторы по убыванию времени. Колонки `REGISTRY_COLUMNS`: №, Время мс, Время %, CPU мс, Ожидание блокировок мс, Блокировал сам мс, Ожидание ресурсов мс, Ожидание ресурсов 1/2/3 место, Выделено памяти МБ, Ожидание клиента мс, Логических чтений, Физических чтений, Выборок, Запусков, Объект, Строка, Хэш, Текст, План, Начало текста. Время оператора = `Δelapsed − client`.
  - `Хэш` (crc32 текста без пробелов и регистра) нужен режиму 2: по нему сопоставляются операторы двух запусков (`read_registry` читает колонку по имени). Пользователь спрашивал, зачем он, — оставлен только в реестре.
  - `Начало текста` (`head_cell`, последняя колонка, без `escape`): первые `REGISTRY_TEXT_LEN=100` символов, заменяются пробелом только `HEAD_BREAKS_RE` — `\r\n` (одним пробелом), `\x00-\x08`, `\x0a-\x1f`, `\x7f`, `\x85`, `U+2028/2029`. Табуляция и прочее как есть (требование: кусок копируется и находится поиском в исходном тексте). Поле в кавычках, если есть `;`, `"`, табуляция или пробел по краю. Поведение Excel с табуляцией внутри поля в кавычках на реальной машине не проверено.
- `log.csv` — журнал отрезков: `LOG_COLUMNS` = «Время сервера» + колонки реестра без №, `Время %`, `Хэш`, `Текст`, `План`, `Запусков` (номера файлов меняются, журнал только дописывается; формат одинаков в `--profile` и `--session`). Связь с реестром — объект + строка (+ начало текста). С `--repeat` — все прогоны со второго.
- `NNN - T.sql` (T — время, мс) — текст оператора; 1-я строка комментария — объект и строка, 2-я — значения реестра (`--Время мс: …; CPU мс: …`), кроме пустых, `Время %` и «Ожидание клиента» (`SQL_COMMENT_SKIP`). `NNN - T.sqlplan` — план.
- **`RegistryFolder.sync(files)`**, файлы как `{имя: (идентичность, текст)}`, идентичность `("sql", key)` / `("plan", key)` / имя служебного файла:
  1. исчезнувшие идентичности забываются;
  2. если у идентичности изменилось только имя, а текст тот же, — `os.replace` (переименование). Переименования идут волнами, пока имя-цель свободно; обмен именами по кругу не переименовывается, а падает в перезапись;
  3. новые и изменившиеся пишутся атомарно (`put`: временный файл + `os.replace`), неизменившиеся не трогаются;
  4. старые имена, которые больше никому не нужны, удаляются.
  Занятый файл (Excel его блокирует) пропускается до следующего раза с одним предупреждением.
- **`LogWriter`** — только дозапись; если файл заблокирован, строки ждут в памяти.

## 9. Режим 3: `--session N`

- Два подключения (`APP=… session`): контрольное (выборки, проверка жизни сессии) и `Lookup` (тексты, объекты, планы). Проверки: не своя `@@SPID`, сессия существует. Папка `Sessions_profile/Session_<время сервера>_N` (`SESSIONS_DIR`, `unique_path`) в текущей папке или `OUTPUT_DIR`: общая папка, чтобы наблюдения не смешивались со скриптами.
- Цикл `SessionMonitor.run`: раз в секунду проверка жизни сессии (по `login_time`, чтобы не спутать с новой сессией с тем же номером) → `poll()` → строка состояния → раз в `SESSION_FLUSH_S=10` с `flush(True)` → ожидание до следующей выборки с проверкой клавиши каждые 20 мс (`msvcrt.kbhit`, без него — только Ctrl+C).
- Выход: клавиша, Ctrl+C, `Stop` (команда `stop`, `--parent-pid`, §3.6), конец сессии, ошибка (код 2). Финальный `flush(False, final=True)` — только диск, без запросов к серверу; запись файла, начатая в момент нажатия, доделывается.
- **Исходный запрос** в шапке `registry.txt` (`input_buffer`): при каждом обычном `flush` один вызов `sys.dm_exec_input_buffer(spid, NULL)` на контрольном подключении; нет функции (до 2014 SP2) — `DBCC INPUTBUFFER(spid)`, нет и его (права) — больше не спрашивается (`input_mode = None`), в шапке «нет данных». Пустой ответ оставляет прежний текст. Одной строкой (пробелы схлопнуты), не длиннее `SESSION_INPUT_LEN`. GUI показывает его под шапкой наблюдения (`inputLine`). Идея — из запроса пользователя в `t.sql` (поле `startScript`).
- **Консоль** (stderr, ≤ `STATUS_WIDTH=79`): `чч:мм:сс объект:строка <30 символов текста> ожидание`. Ключ строки `(запрос, оператор)`. Пока ключ тот же, строка перерисовывается через `\r`, и только если ее текст изменился (`status_shown`; пользователь: не мучить консоль частым выводом — бегущее время на экране считает GUI), при смене — перевод строки и новая; время — сервера, когда оператор впервые попал в выборку (не момент последнего обновления: иначе в истории все строки показывали бы, когда их перестали обновлять; раньше было «от начала наблюдения», пользователь попросил время сервера везде). Длинное имя объекта обрезается с `~`. `warn()` сначала завершает строку состояния.
- `log.csv` дописывается сразу по закрытии отрезка, остальное — при сбросе.

## 10. Режим 2: сравнение

- `parse_report`: проверяет `REPORT_FORMAT_VERSION` (сейчас 2), признак прерванного запуска (такие не принимаются), читает таблицы: файл, строки, хэши, ключ P и его длину, игнорируемые колонки, затраты (`COST_RE` принимает и старый вид без времени → «время нет данных»).
- По каждой таблице (по номеру):
  1. **Структура** (число, имена, порядок колонок). Разные типы одного семейства — предупреждение. Если структура разная, сравниваются только число строк и хэши общих колонок.
  2. **Игнорируемые колонки** — объединение из **обоих отчетов**, не из текущих настроек (иначе сломается соответствие сортировке файлов).
  3. **Быстрый путь**: совпали число строк, хэш таблицы и хэши всех колонок → «идентична», файлы не читаются. Если списки игнорируемых различаются, хэш таблицы не используется.
  4. **Ключи совместимы**, если один — префикс другого: потоковый merge-join по файлам (`iter_side` проверяет порядок и число строк; нарушение — ошибка, код 2). **Иначе** — в памяти: обе таблицы загружаются и сортируются по `common_key` (ключ A, если уникален в обоих; иначе ключ B; иначе объединение, оно уникально в обоих), без игнорируемых и `#dup`.
- `Merger`: группы по общему префиксу ключа без игнорируемых колонок и `#dup` (они стоят в конце ключа, поэтому остаток — тоже префикс). Внутри группы пары по неигнорируемым колонкам более длинного ключа, в порядке файлов. Лишние строки длинной стороны с тем же коротким ключом — «лишние дубликаты по короткому ключу». Сравниваются неключевые неигнорируемые колонки; `FLOAT_TOLERANCE` для float. Счетчики: только в A/B, сопоставлено, отличается, по колонкам, по одному примеру в отчет. Кроме того `examples` — до `EXAMPLE_ROWS=20` строк каждого вида (изменена: ячейки A и B и индексы отличий; только в A/B: ячейки) в порядке ключа; их возвращают `compare_rows`/`compare_table` четвертым элементом (режим 2 их не пишет, показывает GUI, §17).
- **Реестры** (оба запуска с `--profile`): таблица из `registry.csv` (у старых — из `registry.txt`). Сопоставление (`statement_pairs`): по объекту + хэшу текста (одинаковые по порядку); оставшиеся одного объекта — по промежуткам между опорными точками (совпавшие по хэшу, идущие в одном порядке в A и B; номер промежутка — сколько опорных выше по строке своей стороны): в промежутке поровну — по порядку; иначе на одной строке, затем по `STMT_PREFIX_LEN=20` первым символам «Начала текста» (схлопнутые пробелы, casefold), только однозначно; остальное — «(нет в A/B)». Строка A, если отличается, — в пометке («в A стр. N»; ее разбирает `STMT_RE`). История: сначала было «поровну по всему объекту», потом пользователь нашел случай (оператор на той же строке с чуть измененным текстом выходил «нет в B»/«нет в A»: быстрые операторы попадают в реестр не в каждом запуске) — добавили пары по строке; затем пользователь предложил сопоставлять по положению (строка ±1%, не меньше 2) и первым 20 символам для операторов длиннее 3 строк — вместо ±1% взяты промежутки между опорными (сдвиг строк от вставок выше не ограничен процентом, а порядок операторов сохраняется). `statement_changes` возвращает тройки (A, B, пометка), текст строки — `statement_text`; GUI (`compare_details`) вызывает те же функции и берет из строк реестров файлы текста и плана обоих запусков. Рассматриваются верхние `TOP_SHARE=20%` (не меньше `TOP_MIN=5`) по времени в A или B. Значимо: ≥ `SIGNIFICANT_PCT=20%` и ≥ `SIGNIFICANT_MS=1000` мс. Показываются ускорения и замедления.
- Файлы рядом с отчетом B: `<B>__<A>_compare_<время>.txt` (полный) и `_short.txt` (в консоль). Имя начинается с B, чтобы при сортировке стоять рядом с проверяемым запуском.

## 11. Совместимость форматов

- `REPORT_FORMAT_VERSION = 2` не менялась при добавлении времени, подпапок и `registry.csv`: новые поля опциональны при разборе. Поднимать версию только при несовместимом изменении.
- Старые отчеты: без времени (`COST_RE`), без подпапки (данные рядом с отчетом), реестр только в `registry.txt`.

## 12. Исследования и отброшенные варианты

Все выводы ниже получены по источникам (ссылки — в конце раздела) и согласованы с пользователем. Не возвращаться к отброшенному без новых фактов.

| Вариант | Решение | Почему |
|---|---|---|
| `SET STATISTICS IO/TIME` (была в v1) | **убрано** | Разбор текста зависит от языка сервера. CPU вложенных процедур считается дважды: сервер сообщает время каждого оператора и потом общее время `EXEC`, уровень из текста не определить. Главное: на запросах со скалярными функциями увеличивает CPU самого запроса примерно в 5 раз (Brent Ozar: функция на 2,3 млн строк, ~14 с → 70+ с). Заменено контрольным подключением |
| `SET STATISTICS XML` (фактический план) | **отброшено** | Каждое выполнение оператора возвращает отдельный набор с планом: цикл на 1000 итераций — 1000 планов и сильное искажение. Номера строки процедуры в плане нет |
| Extended Events (трассировка системными событиями: `sp_statement_completed`, `sql_statement_completed`, `module_end`) | **отброшено** | Серверный объект: `CREATE EVENT SESSION` и право `ALTER ANY EVENT SESSION` — это изменение конфигурации чужого сервера даже при записи в память. Сеанс принадлежит серверу, а не подключению: при обрыве или убитом скрипте он продолжает жить, автоостановка `MAX_DURATION` есть только в SQL Server 2025. Ring buffer: выдача ограничена ~4 МБ, лишние события не прочитать. Файловая цель: `.xel` остаются в папке логов сервера и средствами T-SQL не удаляются. Фильтр проверяется при каждом операторе каждой сессии, а у пользователя функции вызываются десятки миллионов раз за запрос; оверхед под нагрузкой 9–15 % (Andreas Wolter), у Brent Ozar 2,3 млн событий дали ~1 ГБ. Исключить функции фильтром можно, но проверка все равно идет на каждом вызове |
| SQL Trace (`sp_trace_*`, Profiler) | **отброшено** | Тот же класс (серверная трассировка), а оверхед выше, чем у XE (Jonathan Kehayias) |
| `sys.dm_exec_query_statistics_xml` (живой план) | **исключено** | Известные сбои сервера ровно в нашем сценарии частого опроса на нагруженном сервере: KB4078596 (access violation), KB4490136 (assertion), KB5017788 (затрагивает 2017/2019) |
| `sys.dm_exec_query_stats` / `sys.dm_exec_function_stats` (разница до/после) | **исключено** | Чтение по всему кэшу планов, данные смешаны с работой других сессий над теми же процедурами; Microsoft пишет, что под нагрузкой первый запрос может быть неточным. Поэтому в реестре нет числа выполнений |
| Фактические планы `LAST_QUERY_PLAN_STATS` (2019+) / lightweight profiling | **отброшено** | Требуют настроек базы или сервера. Сохраняются кэшированные планы без фактических строк |
| Очистка кэша для «холодного» замера | **запрещено** | Ударит по всем пользователям. Вместо нее прогрев первым прогоном |
| `sys.dm_exec_query_plan` (XML) | заменено на `sys.dm_exec_text_query_plan` | Текстовый вариант берет план конкретного оператора по смещениям и не упирается в лимит XML на 128 уровней вложенности. Получение плана в 6–20 раз дороже текста, поэтому планы берутся один раз, в конце и только для топ-30 |
| **Выборка `sys.dm_exec_requests` раз в 100 мс** | **принято** | Ничего не создается на сервере, только точечное чтение по одной сессии; рабочая сессия не замедляется. Сэмплирование DMV — обычная практика мониторинга. Проблемы sp_WhoIsActive связаны с его tempdb, не с чтением DMV |

Другие проверенные факты:
- `cpu_time` в `sys.dm_exec_requests` включает дочерние потоки параллельного плана с SQL Server 2012 SP2.
- Чужая сессия видна в DMV только с `VIEW SERVER STATE`, даже если это тот же логин.
- `--rollback` — самый реальный риск для других пользователей: открытая транзакция держит блокировки и не дает усекать журнал транзакций (журнал растет при любой модели восстановления). Поэтому без флага транзакций нет вообще (autocommit), а с `--repeat` откат после каждого прогона. Изначально в ТЗ был `--commit` с транзакцией по умолчанию — пользователь развернул: по умолчанию никаких транзакций.
- `ASYNC_NETWORK_IO`: пока клиент медленно забирает строки, запрос может держать блокировки. Отсюда легкий этап 1 и обработка в отдельном процессе.
- Встроенные (inline) функции и inline-TVF — часть плана запроса, отдельных операторов не дают.

## 13. Что не проверено на реальном сервере

Все сделано и проверено только на имитации драйвера. Список проверок — в конце README («Что проверить на реальном сервере»). Ключевые гипотезы:
- счетчики сессии внутри батча действительно не включают текущий запрос (иначе затраты таблиц задвоятся — тогда поправить `Control.now`);

## 15. Подводные камни

- `CompareQuery.py` и `README.md` сейчас с переводами строк CRLF (их переписывали скрипты Python в текстовом режиме на Windows). Edit их сохраняет; при правке скриптом читать и писать с `newline=""`.
- Bash heredoc в этой среде превращает `"\\n"` в настоящий перевод строки — правки с escape-последовательностями делать через Edit или через скрипт-файл.
- Windows: `*`, `?` недопустимы в именах файлов; файл, открытый в Excel, заблокирован на запись и переименование.
- Вывод в консоль Windows: при печати русских строк из Python в Bash нужен `PYTHONIOENCODING=utf-8`.
- `GO` ищется построчно: внутри `/* */` или строки тоже разделит батч (известное ограничение).
- `real` приходит с хвостом (`0.10000000149…`), `datetime2(7)`/`time(7)` теряют последний знак (pyodbc читает до микросекунд).
- Типы в `create table` приблизительны: драйвер не различает `varchar/nvarchar`, `int/bigint`.

## 17. GUI (`CompareQueryGUI.py`, `gui/`)

Спецификация — `GUI.md` (источник правды для экранов). Технология: pywebview (WebView2) + HTML/CSS/чистый JS без сборщиков.
- **`CompareQueryGUI.py`**: `import CompareQuery as cq` — отчеты читаются его функциями (`fields`, `parse_table`; свой `read_report`, потому что `parse_report` не принимает прерванные), настройки — `cq.SETTINGS_PATH` (один `CompareQuery.json` рядом со скриптом), раздел `"GUI"` (`folder`, `reference`, `params`, `collapsed`, `notes`). Класс `Api` — методы для интерфейса (атрибуты с `_` интерфейсу не видны); `Proc` — процесс CLI с `--events --parent-pid`, `cwd` = рабочая папка (туда же ложится `Sessions_profile`), stdin открыт для `stop`, stdout — события JSON, stderr — строки журнала (строка состояния `--session` через `\r` дает по строке на каждую версию).
- **Время суток — сервера** (§3.8): JS берет смещение из события `clock` процесса (`srvOffset`) и переводит им `time` событий и время старта процесса; сообщения SQL несут свое `server_time`; подписи завершенных запусков и наблюдений — из имен файлов (там уже время сервера). Бегущее время — по часам компьютера.
- **Windows 8.1**: pywebview на каждое перемещение окна пишет «Failed to get DPI for window: GetDpiForWindow not found» (функции нет до Windows 10 1607, pywebview сам берет масштаб 1) — `quiet_dpi_warning`, фильтр логгера `pywebview` только для этого сообщения.
- **Панель** перерисовывается, только если HTML изменился (`side._html`), с сохранением прокрутки дерева: перерисовка раз в секунду, пока идут процессы, теряла клики и сбрасывала прокрутку. `collapsed` и `params` — собственность интерфейса: `refresh` не берет их из ответа `state` (ответ, запрошенный до клика, возвращал старое значение — пользователь видел «срабатывает со второго раза»).
- **Широкие таблицы** (`hbar`): своя полоса прокрутки после `.tscroll`, `position: sticky; bottom: 0` — прилипает к низу окна, пока видна часть таблицы; родная полоса `.tscroll` скрыта. Нужны `.tw{overflow:clip}` (hidden сделал бы карточку областью прокрутки для sticky) и нижний отступ `.main` не через padding (sticky отсчитывается от края содержимого, полоса висела бы на 40 px выше). Отброшены: ограничить высоту таблицы (маленькая при просмотре вплотную или пустое место при паре строк, две вертикальные прокрутки).
- **События в интерфейс — опросом**: JS раз в 250 мс вызывает `poll(seq)` и получает новые события всех процессов. Один механизм для окна и для `--dev`; бегущее время считается по полю `time` событий, а не по моменту получения.
- **Сравнимость, «=»/«≠», Δ%** — по отчетам без чтения CSV (`comparable`, `same_data`; критерии — `GUI.md` §5.13). Подробное сравнение — процесс режима 2, экран показывает текст `_short.txt`.
- **Отличия таблицы** (`table_diff`, `GUI.md` §5.19): `cq.parse_report` опорного (A) и запуска (B) и `cq.compare_table` в процессе GUI — тот же код, что у режима 2, только чтение двух CSV, файлы сравнения не пишутся. Возвращает короткие строки итога (без «Пример …» и затрат) и `examples` (NULL → `None`).
- **Содержимое CSV** (`read_table`): без фильтра — первые `TABLE_ROWS=500` строк, число строк из отчета (раньше файл читался целиком — секунды на больших). С фильтром — весь файл, но строка разбирается, только если текст фильтра есть в ней (тексты ячеек стоят в строке файла как есть, кроме удвоенных кавычек; для фильтра с `"` предпроверки нет).

Новые группы — в начало, `*` — в конец. Ключ в json берется как есть (`ignored_key`: CLI читает ключи без учета регистра). Автоопределение — обычный запуск `--repeat 2` (`S.autodetect`); по выходу из «Предложения для настроек» отчета берется строка JSON, колонки вписываются в область скрипта.
